# Local-first RP-Initiated Logout

This unpublished Java 17 recipe composes an existing authenticated application session with the public OIDC logout API. It creates no identity, account, login flow or general session service. Configure one trusted HTTPS origin, a client using that origin's `/logout/callback`, a client `totalDeadline` of at most three seconds and a confidential, integrity-protected atomic pending store. The handler keeps one original four-second application budget and admits at most eight concurrent operations without a work queue. An injected synchronous application/provider callback can overrun; late results are withheld, and the transport/edge needs its own deadlines.

`Sessions.closeAuthorized(sessionCookie, csrf, remaining)` is an application security boundary. Under one lock or transaction it checks the *current stored session's* CSRF and closes that exact session before returning `Detached(originalReference, retainedHint)`. Return `Denied` only when authorization failed before any close. Return `Unavailable` for an uncertain outcome; null or a thrown failure also means a close may have occurred. The handler never retries, reattaches, rolls back, creates a session or claims confirmed authorization for an uncertain close. Obtain the hint explicitly after genuine completed authentication using the same configured client; retain it with the original comparison-only reference in protected server storage. Current account/tenant authorization and login admission remain the existing application's responsibility.

The fixed `/logout` route accepts an empty same-origin POST, one exact raw Origin, one `X-CSRF-Token`, one canonical 32-byte Base64URL `__Host-app-session` cookie, no query, no Authorization header and a complete bounded body. The callback atomically verifies the CSRF's stored session binding before any close or provider work. Never accept transport trust from forwarding headers. Preserve raw header/cookie multiplicity and complete-body/discard status. The common handler caps inputs at 32 headers/8 KiB and bodies at 4 KiB; the selected flow requires an empty body. Cookies use Secure, HttpOnly, Path=/ and SameSite=Lax, with no Domain.

After a confirmed local close, the handler prepares the core logout request, creates a fresh independent 32-byte browser binding and saves pending state once with the shrinking application budget. Only SAVED permits browser delivery. Unavailable, refused, late, null or uncertain operations never restore the local session or permit automatic retry. Possible-close failures expire the relevant old application cookie; they do not claim that the close was confirmed. A pending row saved before a final output failure may remain until its bounded expiry, without issuing its browser binding.

Trusted startup chooses `Delivery.FORM_POST` (recommended) or `GET_REDIRECT`. Form delivery uses escaped hidden fields, a fixed trusted action, no script, restrictive CSP, no-store and no-referrer; the user presses the provider continuation button after local sign-out. Explicit response bodies or Location headers contain the retained ID-token credential and must never be logged. GET delivery refuses a redirect URI over 4096 ASCII bytes instead of switching modes or raising carrier limits. This bound is not a browser/provider interoperability qualification.

`GET /logout/callback` passes only the bounded raw state query and the independent browser-binding cookie into the core return API. Clear that pending cookie on every callback delivered to the handler, including carrier rejection and exceptions. A parser or transport failure before a callback reaches the application may prevent any cookie-clearing response; it does not create correlation or restore a local session. The return never clears a newer application-session cookie, creates a session, discovers metadata, fetches keys, verifies a new ID token or contacts the logout endpoint. Returned means correlation only, not proof of provider-session termination. The callback URI comes from fixed trusted routing, never request headers.

The test fixture will use a bounded atomic session map populated only after genuine synthetic OIDC authentication; no fixture-only login/control route belongs in the production handler. In-memory process-local sessions/pending stores do not qualify a durable multi-node deployment. Real Soklet and paired Servlet carrier checks, an authenticated HTTPS/query-rejection edge, real browsers/providers, independent qualification and final source/artifact joins are separate gates.
