# PostgreSQL storage examples

These application-side examples implement PostgreSQL storage for OAuth, OIDC and WebAuthn flows that can reach different JVMs. They use Pyranid 4.7.0 for bound SQL and transaction lifecycle against one authoritative primary. The Revetsec core artifact retains zero runtime dependencies.

Apply `schema.sql` with your migration tool, then create one clock row for a **new** stable namespace. Pass the same namespace and database to every JVM. For example:

```java
var store = new PostgresqlPendingAuthorizationStore(
    "my_application", connectionSource, 1_024, 8 * 1_024, 4L * 1_024 * 1_024);
```

`connectionSource.open(remaining)` is application-owned and thread-safe. It must bound pool acquisition, DNS and connection setup by the shrinking budget, return a distinct logical connection to the authoritative primary for each call, and preserve the normal PostgreSQL TLS/certificate policy. The example sets a driver network timeout and a transaction-local statement timeout for subsequent SQL. Connection sources that can block without honoring `remaining` do not meet the `PendingAuthorizationStore` contract.

The example caps one database operation at one minute even if a caller supplies a longer budget. It never extends a shorter caller budget.

Every operation locks the namespace clock row. It stores the largest observed database instant, so an observed backward clock step cannot revive an expired record. Save prunes expired rows, rejects a duplicate live key and refuses capacity without evicting live logins. Consume removes once across JVMs. The browser binding and state are hashed for the table key; the opaque record is stored as plaintext and contains sensitive pending authorization data, so applications must protect database access, transport, backups and logs.

The result is released only after Pyranid reports a confirmed COMMITTED transaction. A failed or uncertain commit produces a fixed storage failure; callers must not automatically retry a callback or treat an uncertain save as successful. The local fixture injects a lost COMMIT acknowledgement after the database commit and verifies both application boundaries: the save path withholds its redirect, and the callback path withholds tokens and makes no token request. A consumed record may be lost under an uncertain commit, requiring a new login. The application owns database credentials, capacity settings, migrations, monitoring, backups and restore admission. A restored snapshot can restore an authentically consumed record and an older clock fence; keep routes closed until the application's external recovery fence and key procedure are complete. This source does not establish high availability, cross-host failover or power-loss durability on its own.

## Optional shared CIMD metadata cache

The companion `PostgresqlClientMetadataCache` implements `OAuthClientMetadataCache` for compatible authorization-server nodes. Apply the `cimd_cache_*` tables in `schema.sql`, provision a new stable cache namespace, and select it through `OAuthClientMetadataPolicy.Builder.cache(...)`. The cache uses Pyranid-managed transactions and oldest-write-first eviction, capped at the configured entry count. Its application-supplied connection source must bound acquisition and return clean, distinct connections to the same primary. This optional cache never replaces the authoritative authorization-server store or pending-authorization store.

It persists Revetsec's bounded encrypted carriers exactly. Revetsec still authenticates and evaluates each hit under current issuer, client, policy and freshness rules; each credential transition still requires its own successful fresh metadata fetch. An expired carrier can remain in storage until eviction and is not permission to use the document. A failed or uncertain cache write reports a fixed failure, which may require a read to reconcile; the caller must not treat it as a successful compare-and-set. A database outage is a failure, not a confirmed miss. Cache restoration, eviction and node changes cannot turn a carrier into a credential or a fresh-fetch proof. This example demonstrates one PostgreSQL primary and independent JVMs on one host, not cross-host high availability.

## Optional authoritative issuer store

`PostgresqlIssuerStore` implements the application-owned `OAuthAuthorizationServerStore` for a shared issuer. Apply the `issuer_store_*` tables in `schema.sql`, provision a stable namespace before the issuer's first initialization, and configure every issuer JVM with the same namespace and primary:

```java
var issuerStore = new PostgresqlIssuerStore("my_issuer", connectionSource, 100_000);
// Supply issuerStore to OAuthAuthorizationServer.Builder.store(...).
```

The storage examples use Pyranid 4.7.0 for bound SQL and transaction completion. Pyranid and the PostgreSQL driver remain application dependencies and do not enter Revetsec core. The issuer store's connection source must open a clean, distinct primary connection within the supplied remaining budget, including pool acquisition and connection setup; normal deployments must preserve their PostgreSQL TLS and certificate policy. The store requires an actual primary with `fsync` and `full_page_writes` enabled and sets transaction-local `synchronous_commit=on`.

Every read and commit locks the provisioned namespace row. A commit compares the entire engine-provided read set, including confirmed absence, before applying its mutations. A predicate conflict has zero effects; a lost COMMIT acknowledgement returns `UNKNOWN` even if the database applied the write. The application must reconcile that outcome before repeating a non-idempotent operation. Entries are never automatically evicted: capacity refusal is safer than dropping an active grant, replay tombstone or permanent issuer/subject fence. Any operator cleanup must obey the same namespace lock and Revetsec retention horizon. Keep issuer routes closed during restore until the application's external recovery fence and key procedure establish safe admission.

The local probe uses ephemeral keys and a fixed synthetic clock. It checks fresh initialization, cross-JVM code issuance and redemption, atomic two-JVM code and refresh races, grant invalidation on credential reuse, isolation of another grant, cross-JVM refresh rotation, online token status, a closed issuer read during database outage, persistence of live and revoked grants across a PostgreSQL restart, and global revocation. A held PostgreSQL namespace lock makes short-budget token status and global revocation fail promptly; releasing it leaves the existing grant active. The probe also checks that lowering the configured capacity refuses new issuance without evicting an existing grant or breaking a condition-only status read. In a separate fixture namespace, removal of a permanent subject fence causes an established grant's status check to fail closed while the unaffected namespace remains available. Never remove such a fence in a deployment or call fresh initialization to repair it.

Uncertain initialization, code redemption, refresh and subject-revocation COMMIT outcomes are reported without claiming success. Uncertain token commits withhold credentials; separate JVMs observe the committed code consumption or refresh rotation by rejecting reuse. After the fixture's uncertain subject revocation, a separate JVM observes its prior grant inactive; a new grant in the advanced subject epoch is then active until another confirmed subject revocation. An inactive token alone is not a general operator reconciliation procedure or permission to repeat an epoch advance. This is one-host, one-primary evidence; it does not qualify cross-host failover, power-loss durability, a production connection pool or an application restore procedure.

## Optional authoritative WebAuthn store

`PostgresqlWebAuthnStore` implements `WebAuthnStore` for a shared relying party. Apply the `webauthn_store_*` migration and provision a new stable namespace before traffic. Select it through `WebAuthnRelyingParty.Builder.store(...)` and configure every participating JVM with the same namespace and authoritative primary. The connection source must open a fresh, clean primary connection within the shrinking budget and preserve the deployment's PostgreSQL TLS/certificate policy. The store accepts only keys belonging to its configured namespace.

Every read and commit locks the provisioned namespace row. A commit compares the complete versioned snapshot, including confirmed absences, before changing any row. A PostgreSQL sequence gives replacements and delete/reinsert cycles non-reused live versions. Capacity refusal never evicts a ceremony, credential tombstone or account fence. The store checks primary status and durability settings and uses transaction-local `synchronous_commit=on`. A lost COMMIT acknowledgement returns `UNKNOWN`; the caller must withhold WebAuthn proof and reconcile authoritatively before another transition. The application owns sealing-key persistence, migrations, connection pooling, account coordination and an external restore admission fence. Restoring an older database snapshot without that fence can revive old challenge or account state.

`run_webauthn.py` compiles the store and probes with warning-fatal Java 17 settings, then uses a disposable PostgreSQL primary. The storage probe checks complete atomic reads and writes, stale predicates with zero effects, non-reused versions, capacity refusal, namespace isolation, a two-JVM one-winner race, lost COMMIT acknowledgement followed by a separate-JVM read, a held-lock deadline, outage closure and persistence through primary restart. It uses synthetic sealed-form bytes to qualify the storage SPI.

The second probe calls the public `WebAuthnRelyingParty` API with a synthetic Ed25519 authenticator. Separate JVMs prepare and complete registration, discoverable sign-in and account-pinned reauthentication; they also list and remove the credential. It checks replay rejection, one verified proof from two concurrent completions, persistent sign-in after primary restart, no browser options during outage, and rejection after server-side removal. A lost COMMIT acknowledgement on authentication completion returns `Indeterminate` without proof; a separate JVM then observes the ceremony consumed. Removal leaves a permanent credential-ID tombstone that prevents reassignment. The run-local signing key is held in runner memory and passed by environment only, without printing it in the runner output.

Passing the pinned Soklet 4.0.0 artifact as `--soklet-jar` adds the optional application route lane. It compiles the same `PasskeyApp` used by the browser demo, injects a stable app-owned account handle and PostgreSQL-backed relying party, and runs each application probe command in a fresh JVM. The app registers a credential through its routes, then signs in and reauthenticates after a database restart. An already running JVM with an authenticated session closes its account page, sensitive action and credential listing when the external marker changes. Later JVMs remove the credential and reject it at sign-in. An uncertain begin closes that app process; an externally advanced marker closes a new process. A logical restore brings back the exact earlier sealed credential row, but the still-advanced external marker keeps the restored app's routes closed. The lane uses synthetic responses and direct route calls; it does not exercise a browser, a TLS edge, load-balanced browser sessions or cross-host operation. Soklet, Pyranid and the PostgreSQL driver are example dependencies only.

Supplying absolute `--browser-node`, `--browser-chrome` and `--browser-openssl` paths along with `--soklet-jar` adds a separate real-browser lane. It generates a disposable exact-DNS HTTPS leaf, runs the same Soklet `PasskeyApp` with the PostgreSQL store and a stable account handle, and keeps one Chrome CTAP2 virtual authenticator alive across two Soklet process restarts. Browser registration survives the first restart; a deliberately bogus signature is rejected, then discoverable sign-in and reauthentication succeed. During a controlled PostgreSQL outage, the account page and sensitive action return 503; returning the same primary permits the one-use step-up exactly once. Server-side removal survives the second app restart and the same authenticator can no longer sign in. The app uses the same reentrant local recovery gate as its relying party, holding a permit through each route handler and any browser-session transition. Browser sessions remain process-local and expire on restart. This is one host, one primary and a test-only local recovery gate; it does not establish physical FIDO2 key, cross-host admission, distributed sessions or production TLS-edge behavior. Soklet, Pyranid and the PostgreSQL driver are example dependencies only.

For example, from the core checkout after building its JAR, use `python3 examples/postgresql-pending-store/run_webauthn.py --help` for the six required artifact paths, add `--soklet-jar /absolute/soklet-4.0.0.jar`, and pass the three browser tool paths. The browser lane needs an OpenSSL binary with `verify -verify_hostname`, Node with built-in WebSocket, Chrome with DevTools virtual-authenticator support, Docker and loopback sockets. The runner cleans up its private TLS directory, Chrome profile, container and volume.

`WebAuthnFixtureRecoveryGate` is a test-only, one-host implementation of the application admission contract. It holds a shared OS file lock for each operation and compares a control-file epoch and sealing-key digest with the `webauthn_recovery_epoch` row. The runner proves an exclusive restore lock cannot pass a live permit, advances the external epoch, and restores an earlier PostgreSQL logical dump containing an unconsumed ceremony and active credential. Their exact stored state reappears, but the older database epoch cannot acquire a permit, so the public API releases no browser options, credential list or authentication proof. A changed sealing key also closes admission. The runner deliberately leaves this restored state closed; an operator would need a separately reviewed reconciliation and key procedure before reopening. The control file is only a local fixture stand-in for a separate durable, cross-host marker and lock; it does not qualify HA, crash durability, unsupervised rollback detection or a production restore process. Run `python3 run_webauthn.py --help` for the six artifact paths. A physical FIDO2 key remains a separate release gate.

`run.py` compiles the example with warning-fatal Java 17 settings and exercises duplicate, expiry, capacity, rollback fencing, browser binding, cross-JVM single use, lock timeout, database outage and restart against a cached disposable PostgreSQL image. A loopback-only synthetic token endpoint checks the authorization-code form and persisted PKCE verifier: a valid callback redeems once, replay and wrong-browser binding send no token request, and simultaneous callbacks in two JVMs produce exactly one redemption.

The OIDC lanes verify cross-JVM identity release, wrong-nonce and bad-signature rejection, and one winner in callback races. The HMAC lane explicitly opts into Revetsec's compatibility mode with a run-local secret. The RS256 lane generates a fresh key pair inside a test JVM and serves its public JWKS from the loopback provider; the private key is never written to disk or included in the runner output. These are local protocol fixtures, not real-provider or cross-host qualification.

The runner also checks cross-JVM cache reads and compare-and-set races, bounded eviction, uncertain COMMIT, confirmed reads despite a connection-close acknowledgement failure, outage and restart. It requires absolute paths to a current core JAR, Java home, and the pinned Pyranid, PostgreSQL, JSpecify and JSR-305 JARs; run `python3 run.py --help` for the arguments. Docker resources, the local endpoint and test credentials are removed after the run.

To include the self-issued Soklet application lane, also pass `--adapter-jar` for the matching Revetsec/Soklet helper and `--framework-jar` for the pinned Soklet 4.0.0 JAR. The runner compiles the current app source with the Pyranid store, then runs fresh and established application instances in separate JVMs against a dedicated PostgreSQL namespace. It checks an issued token across startup, refusal to reinitialize an established issuer, rejection with the wrong sealing key and refresh rotation across JVMs. An established Soklet process then serves OAuth metadata and JWKS over an actual loopback HTTP listener, returns an active introspection verdict, and accepts the persisted token on its MCP listener while denying a missing bearer. Refresh replay in another JVM revokes that token; the still-running Soklet process rejects its next MCP call and returns an inactive introspection verdict.

The fixture's application-owned key provider reads an atomic generation marker from its private temporary directory. During a live Soklet process, the runner changes from the initial RSA signing key to a second ephemeral key while retaining the first public key through a declared retirement boundary. It verifies overlapping JWKS publication, new-key signing, continued old-token admission, and new-token admission from another JVM. An attempted removal of the old public key before that boundary makes JWKS and protected-resource admission unavailable; restoring the retained-key snapshot restores admission. This exercises Revetsec's observed lifecycle guard, not durable key distribution: an application must persist the generation, publication and retirement history and publish changes to all nodes before advancing its provider.

The application fixture also runs two established Soklet JVMs at once. The second binds IPv6 loopback while the first binds IPv4 loopback, using the same issuer and resource ports and checked public Host values; Soklet's MCP listener requires its configured public port. A scripted HTTP client logs in on the first node, reads and approves consent on the second, redeems the code on the first, and calls the second node's MCP resource. A second consent submitted concurrently to both nodes has one redirect winner and one denial; its code redeems once. During a primary outage, both live nodes return unavailable for browser sessions and protected MCP access. This is a single-host, single-primary application fixture, not load-balancer, real-browser, cross-host or HA qualification.

The established app fixture also loads one separate admission partition key from private temporary storage. Its first and restarted Soklet processes produce the same HMAC partition for the same subject, independent of signing-key rotation and token refresh. A real distributed deployment must provision that key consistently and supply a shared Soklet `McpRateLimiter` if it needs aggregate rate limits; the demo's one-argument configuration keeps counters in each process. This partition key does not replace issuer signing/sealing keys, session storage or the authoritative grant store.

The application lane now selects `PostgresqlBrowserSessions`, a test application implementation of `BrowserSessionStore`. Apply the `issuer_browser_*` migration and provision its separate namespace before browser traffic. It serializes reads and writes through the namespace row on one authoritative primary, records a monotonic application-clock fence, stores only SHA-256 of the random cookie ID as its lookup key, and seals the session/CSRF/browser binding/pending action under a context containing that key and namespace. Login atomically deletes the old cookie session and inserts the rotated one; consent claims its pending action in a confirmed transaction before core completion. An uncertain claim withholds the response and may require starting a new authorization. The fixture checks two-JVM claim contention, a rotated cookie and pending consent across a Soklet restart, invalidity of the pre-login cookie, and 503 during database outage. The test backend's fixed five-second budget and direct connection acquisition are illustrative; production pools and shared deployment control still belong to the application. As with issuer grants, an authentic database rollback needs external admission fencing before reopening browser routes.

A scripted HTTP client also completes the app's login and consent forms on the first established Soklet process. The runner stops that process before redeeming its issued code, starts another established process with the same keys and stores, continues a second pending consent under the rotated cookie, rejects the pre-login cookie, and redeems both issued codes at the actual token endpoint. The resulting token reaches the restarted MCP listener. While that listener remains up, the runner stops its PostgreSQL primary: browser sessions, MCP and introspection report service unavailability instead of invalid credentials, and the token endpoint releases no credential. Returning the same primary on a fixed run-local loopback port restores admission of the original token. Reusing the code then releases no new credentials and revokes that grant; the live MCP listener and a third JVM both observe the revocation. This is a local HTTP integration check, not an independent browser qualification. The probe acquires JDBC connections for Pyranid; all store SQL and transactions stay in Pyranid. Its fixture connection source and ephemeral file keys do not qualify a production pool, managed key lifecycle, cross-host session recovery or admission after backup restore.
