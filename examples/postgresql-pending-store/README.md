# PostgreSQL storage examples

**Closed migration/restore fixture — 2026-10-30:** see the unpublished [administrative migration fixture](../../verification/shared-clock-migration/README.md) for bounded inventory/fit, exact prepared batches, uncertain-outcome reconciliation and disposable retained-data/restore checks. This is a closed operator procedure, not an online schema upgrade. Structural activation does not grant timed service admission. Approved witness/profile evidence and target-specific deployment inventory/authorization remain required before any real migration.

The fixture's adapter-join lane starts with the frozen legacy tables, including WebAuthn's `TIMESTAMPTZ`-only retention column. It derives exact retention from authenticated legacy payloads, preflights the prepared target before the first rewrite, and installs the current schema, namespace/admission metadata, registries, capacity reservations and version continuation in place. It then exercises these actual adapters against migrated rows under a scripted witness profile. Pending or uncertain schema/migration intent keeps admission closed. This closes the source integration checkpoint; it supplies no real-deployment UTC, durability or recovery qualification.

These application-side examples implement PostgreSQL storage for OAuth, OIDC, WebAuthn and TOTP flows that can reach different JVMs. They use Pyranid 4.7.0 for bound SQL and transaction lifecycle against one authoritative primary. The Revetsec core artifact retains zero runtime dependencies.

Apply `schema.sql` with your migration tool, then create one clock row for a **new** stable namespace. Pass the same namespace and database to every JVM. For example:

```java
var store = new PostgresqlPendingAuthorizationStore(
    "my_application", connectionSource, 1_024, 8 * 1_024, 4L * 1_024 * 1_024);
```

`connectionSource.open(remaining)` is application-owned and thread-safe. It must bound pool acquisition, DNS and connection setup by the shrinking budget, return a distinct logical connection to the authoritative primary for each call, and preserve the normal PostgreSQL TLS/certificate policy. The example sets a driver network timeout and a transaction-local statement timeout for subsequent SQL. Connection sources that can block without honoring `remaining` do not meet the `PendingAuthorizationStore` contract.

The example caps one database operation at one minute even if a caller supplies a longer budget. It never extends a shorter caller budget.

Every operation locks the namespace clock row. It stores the largest observed database instant, so an observed backward clock step cannot revive an expired record. Save prunes expired rows, rejects a duplicate live key and refuses capacity without evicting live logins. Consume removes once across JVMs. The browser binding and state are hashed for the table key; the opaque record is stored as plaintext and contains sensitive pending authorization data, so applications must protect database access, transport, backups and logs.

The result is released only after Pyranid reports a confirmed COMMITTED transaction. A failed or uncertain commit produces a fixed storage failure; callers must not automatically retry a callback or treat an uncertain save as successful. The local fixture injects a lost COMMIT acknowledgement after the database commit and verifies both application boundaries: the save path withholds its redirect, and the callback path withholds tokens and makes no token request. A consumed record may be lost under an uncertain commit, requiring a new login. The application owns database credentials, capacity settings, migrations, monitoring, backups and restore admission. A restored snapshot can restore an authentically consumed record and an older clock fence; keep routes closed until the application's external recovery fence and key procedure are complete. This source does not establish high availability, cross-host failover or power-loss durability on its own.

## Optional shared CIMD metadata cache

The companion `PostgresqlClientMetadataCache` implements `OAuthClientMetadataCache` for compatible authorization-server nodes. Apply the `cimd_cache_*` tables in `schema.sql`, provision a new stable cache namespace, and select it through `OAuthClientMetadataPolicy.Builder.cache(...)`. The cache uses Pyranid-managed transactions and oldest-write-first eviction, capped at the configured entry count. Its application-supplied connection source must bound acquisition and return clean, distinct connections to the same primary. This optional cache never replaces the authoritative authorization-server store or pending-authorization store.

It persists Revetsec's bounded encrypted carriers exactly. Revetsec still authenticates and evaluates each hit under current issuer, client, policy and freshness rules; each credential transition still requires its own successful fresh metadata fetch. An expired carrier can remain in storage until eviction and is not permission to use the document. A failed or uncertain cache write reports a fixed failure, which may require a read to reconcile; the caller must not treat it as a successful compare-and-set. A database outage is a failure, not a confirmed miss. Cache restoration, eviction and node changes cannot turn a carrier into a credential or a fresh-fetch proof. This example demonstrates one PostgreSQL primary and independent JVMs on one host, not cross-host high availability.

## Optional authoritative issuer store

`PostgresqlIssuerStore` implements the admitted-time schema-2 `OAuthAuthorizationServerStore` contract. Apply [issuer-schema.sql](issuer-schema.sql) only to a fresh namespace or under a complete admission-closed conversion procedure; this is not an online upgrade of legacy rows. Provision the logical fixture namespace, canonical physical namespace ID, authority/recovery/clock generations, fixed UTC-error profile, allocation generation, format 2, capacity and all 256 assigned entry escrows together. The constructor requires an independent trusted authority:

```java
var issuerStore = new PostgresqlIssuerStore("my_issuer", physicalNamespaceId,
    connectionSource, 100_000, trustedAuthority);
```

The authority is application-owned and independent of worker `Clock` and PostgreSQL wall time. Every participating JVM uses the same primary, admitted metadata, physical scope and sealing/recovery lifecycle. The connection source opens a fresh clean primary connection within the shrinking budget and preserves deployment TLS/certificate requirements. Pyranid 4.7.0 and the JDBC driver remain application dependencies. The fixture verifies primary `fsync`/`full_page_writes` and transaction-local synchronous COMMIT.

Ordinary callbacks take shared physical admission, sorted strongest logical-key transaction locks including confirmed absences, then changed escrow buckets. Fresh issuer-root insertion takes exclusive admission first. A permanent per-issuer root registry commits atomically with activation; missing registered roots and orphan data refuse initialization. Normal paths have no namespace-row mutex, global count/sum, read cleanup or timestamp write. Exact opaque versions and the full read set precede fresh authority sampling after all waits; inclusive floor and exclusive expiry precede assigned capacity checks and atomic data/quota DML. An assigned bucket may refuse while another has room. Permanent issuer/subject records cannot be deleted or evicted. Replay state retains its full exact seconds/nanos retention.

`read` returns a coherent `OAuthStoreReadResult`; UTC-unavailable data admission is explicit. When independent authority/recovery admission matches but a Healthy clock/error profile is not admitted by the SQL mirror, the coherent entry retains that admission with unavailable time. Only the narrow fence path can use it; timed writes remain fenced. Authority/recovery mismatch, missing activation/root or an uncertain read never receive this downgrade. `commit` returns the contextual receipt and preserves known COMMITTED even after late acknowledgement or cleanup failure; lost acknowledgement after a possible write is UNKNOWN and permits no automatic retry. Optional completion timing is omitted. The engine separately performs its minimum-root final admission read before normal service output. Raw initialization/reseal return factual receipts and do not imply readiness. Finite reseal is bounded by original full retention, allowing retained credential-expired state without admitting it.

Narrow `FENCE_ONLY` transactions advance only an existing issuer or subject epoch with exact permanent predicates, same authority/recovery admission and no timed condition. They can commit during an admitted UTC outage. The engine authenticates preservation of floors, minima, binding and retention and takes its no-UTC minimum-root acknowledgement read. Token revocation HTTP, issuance, subject creation and reseal cannot use this mode.

[run_issuer.py](run_issuer.py) is the bounded source-bound SCP-08 lane. It uses genuine engine-generated transactions, an independent scripted authority channel, a nonprivileged runtime role and an owned disposable one-primary PostgreSQL fixture. It compiles/audits the complete selected source closure, exercises temporal refusal and fence-only receipt forms, issuer workflows, replay, capacity and missing-root refusal, and records exact artifact/source hashes and cleanup. The broader [run.py](run.py) and the separate [issuer verification fixture](../../verification/issuer-store/README.md) retain their own scope. No scripted source qualifies approved UTC accuracy, witness-owner integration, device durability, actual old-binary/pooled-session exclusion, retained-data conversion or a combined-family deployment.

## Durable TOTP fixture

The unpublished `PostgresqlTotpStore` implements the admitted-time `TotpStore` contract for the Java 17 TOTP and recovery-code API. The separate [TOTP schema](totp-schema.sql) describes a fresh or admission-closed, fully migrated namespace; it is not an online alteration of the legacy schema. Provision its logical credential namespace, canonical 43-character physical namespace ID, exact authority/recovery/clock generations, UTC-error profile, allocation generation, capacity and all 256 escrow buckets together. Provision one never-reused initial address epoch in both namespace and epoch tables. Existing retained data needs the separately planned closed inventory, codec conversion, capacity reservation and old-writer exclusion before this writer may run. The namespace begins as `NEW`; call `TotpAuthenticator.initializeNamespaceResult()` through the recovery gate, confirm `Initialized`, then open ordinary admission. Every participating JVM must use the same authoritative primary, physical scope, externally controlled address epoch and sealing-key lifecycle. The required constructor accepts an independent trusted `Authority`; neither the worker `Clock` nor PostgreSQL timestamps supply authority time. The `ConnectionSource` must open a clean primary connection within the shrinking budget, including connection acquisition and network setup, and preserve the deployment's TLS/certificate policy.

Ordinary reads and commits take shared physical admission, sorted logical-key locks including absence predicates, and changed escrow buckets in that order. They do not take a namespace-row mutex, calculate global count/sum totals, prune records or write an observation fence. Commit validation compares the exact versions/absences and SQL admission tuple, samples fresh authority time after all lock waits, applies the inclusive floor and exclusive expiry, and then checks assigned bucket capacity. Data and K64 byte reservations commit atomically; a bucket may refuse capacity while another bucket still has room. The rare namespace-initialization commit takes exclusive physical admission first, then atomically inserts the permanent TTR3 root and changes `NEW` to `ACTIVATED`; a missing root after activation is unavailability. Account and namespace records, including removal tombstones and old-epoch records, have no TTL or deletion path. The fixture checks a primary with `fsync` and `full_page_writes` enabled and sets transaction-local `synchronous_commit=on`. A known commit retains its required validation timing even if acknowledgement arrives late; optional completion sampling is absent. A lost COMMIT acknowledgement is `UNKNOWN` after a possible write, even when the database applied it; no TOTP proof or recovery plaintext may be released on that result. `provisionRecoveryEpoch` remains separate factual administration and does not reset the shared authority, recovery or clock generation.

`TotpFixtureRecoveryGate` and `TotpFixtureRecoveryController` are test-only one-host application collaborators. The external marker is outside the restorable database and binds the exact namespace, epoch, active/opening sealing-key IDs and SHA-256 digests of their material. Shared OS file locks hold admission across each core operation and the application completion path; an exclusive controller lock drains live permits. The controller permits only explicit namespace initialization in `INITIALIZING` mode and ordinary traffic in `OPEN` mode. It writes `CLOSED` before waiting for the drain. After a PostgreSQL logical restore, keep the exclusive lease while the store transactionally advances to a fresh, never-reused epoch. Publish that fresh marker while still holding the lease, release it, explicitly initialize the new root, and only then open ordinary traffic. Earlier application sessions, pending logins and approval markers are rejected by their epoch checks even if the restore brought their rows back. Restored old factors and recovery codes require application-approved recovery and reenrollment. The database's own epoch history can roll back with its backup; the separate marker is the fixture's authority for freshness.

The separate `TotpApplicationSessionStore` and `TotpApplicationSessionProbe` are **test-only application code**, not part of the Revetsec API or a production session implementation. `seed` simulates primary authentication and creates a short-lived pending login with a primary session, cookie/CSRF digests, expected factor ID and recovery epoch. Before invoking core, the probe checks that pending binding, account, current epoch, primary session and CSRF. A confirmed TOTP or recovery-code proof is followed by a separate application transaction under the same held external permit. That transaction locks the authoritative namespace row, checks the active epoch and pending/session predicates again, compares the proof's account, binding and factor ID with the pending record, consumes the pending login, revokes the old session and creates a new cookie and CSRF token. A TOTP proof creates a `TOTP` session; recovery-code use creates a restricted `RECOVERY_CODE` session. Only a `TOTP` session can create the fixture's short-lived, session-linked synthetic approval marker; the primary and recovery sessions cannot. The marker is an epoch-fencing probe, **not** an action-bound, one-use management approval.

Every application read and transaction also advances a per-epoch high-water clock under that namespace lock, failing closed on backward time so an expired row cannot revive on the same epoch. Application commit acknowledgement uncertainty withholds the new cookie/CSRF even when the database consumed the pending login. Core may already have consumed the valid TOTP step or recovery code before an application completion fails; the application cannot treat that proof as a committed session. This fixture holds one application admission permit across both operations, but it does not make the two database commits atomic with each other. A production application must provide real primary authentication, account/MFA policy, purpose-bound approvals, session and CSRF controls, operator recovery and a durable cross-host admission mechanism if deployed across hosts.

The [Java 17 runner](run_totp.py) compiles the store, gate and probes with warnings fatal and runs against a disposable, loopback-bound PostgreSQL primary. It declares a TOTP-only fixture family allowlist and uses `TotpFixtureAuthority`, a scripted test source with input separate from worker time. This source does not establish approved UTC accuracy or join the private witness owner process. Its structural storage lane uses deliberately unauthenticated synthetic sealed carriers to test complete snapshots, atomic predicates and mutations, required timing, exclusive initialization admission blocking an ordinary shared reader, exact temporal refusals after entity/quota waits, zero-mutation barriers, K64 bucket capacity, late known commit, uncertain acknowledgement, outage and restart. The genuine public-API lane generates authenticated TTR3 writes through the engine in independent JVMs for enrollment and confirmation, concurrent TOTP and recovery-code consumption, replay rejection, post-COMMIT lost acknowledgements that withhold proof while consuming the step/code, and persistence after primary restart. A worker clock one day ahead of authority time closes confirmation and status without changing data or quota; a healthy worker can then confirm normally. The application lane checks pre-proof rejection of wrong pending binding, cookie or CSRF; confirmed cookie/CSRF rotation; failed-code and uncertain-commit handling; a backward application-clock fence; a two-JVM, one-winner recovery session completion after two distinct valid codes; and denial of synthetic approval from primary or recovery sessions. It pauses after a valid proof to show that a controller closing admission before application completion withholds the session, then advances the application clock beyond the pending-login deadline after another valid proof and checks that completion is rejected while the old primary session remains. After recovery into a fresh epoch, it pins a pending login to one factor, removes that factor, enrolls another and confirms that a valid proof from the replacement factor cannot complete the old pending login. The logical-backup lane includes application rows and checks that restored old sessions, approvals and pending logins remain unusable in the new epoch. The key lane drains admission to change the active sealing key, reconciles an uncertain namespace reseal from another JVM, reseals the account, retires the old key, and checks that consumed steps and codes remain consumed while an unused code still works. The runner keeps synthetic setup and recovery secrets in process memory rather than its receipt.

The first admission-close pause checks the proof-to-completion boundary. A second pause occurs after the final application session `INSERT` inside an open Pyranid transaction: a separate PostgreSQL connection confirms the namespace row lock with `FOR UPDATE NOWAIT`, and the controller cannot finish draining until that transaction and its outer permit end. If admission closes during this in-flight transaction, the database may commit the session change, but the probe withholds the cookie and CSRF and confirms the consumed pending login. These are one-host fixture checks, not a production session or cross-host recovery qualification.

The runner also makes a reproducible sizing observation: by default, four JVMs each perform eight authoritative read-plus-unique-insert operations sharing physical admission and assigned buckets. `--workload-workers` and `--workload-operations` set those dimensions. The receipt records completed operations, wall time, throughput and p50/p95/p99 operation latency; it asserts only that every insert committed and is durable. These numbers are for the disposable one-CPU, 256 MiB, one-host primary, and are not production capacity or latency targets. Size a deployment with its own pool, primary, record population, traffic mix and recovery controller.

## Optional authoritative WebAuthn store

`PostgresqlWebAuthnStore` implements the admitted-time `WebAuthnStore` contract for a shared relying party. Apply the separate [WAR2 schema](webauthn-schema.sql) only to a fresh namespace or under a complete closed migration procedure. It is not an online alteration of the legacy `schema.sql` tables. The required constructor takes that physical ID and a trusted `Authority` separate from the worker clock; no database timestamp or old-constructor fallback supplies time. Every participating JVM must use the same primary, admitted metadata and sealing/recovery lifecycle. The connection source must open a fresh clean primary connection within the shrinking budget and preserve the deployment's PostgreSQL TLS/certificate policy.

Ordinary reads and UPDATE transactions acquire shared physical admission, then sorted strongest-mode logical-key locks protecting every version and confirmed absence, then any changed escrow buckets. A first namespace-root insertion starts with exclusive physical admission. A per-RP activation registry commits atomically with that root; a missing registered root is unavailable and cannot be lazily recreated. The registry is not an external recovery witness. The backend samples fresh authority time after all lock waits, checks the exact admission/profile and inclusive floor/exclusive expiry, then validates assigned capacity before atomic data/quota writes. There is no ordinary namespace-row mutex, global count/sum, observation write or cleanup. An assigned bucket may refuse while another bucket still has capacity. Replacements and ceremony delete/reinsert cycles receive non-reused live sequence versions. The engine authenticates and evaluates ceremony expiry. Permanent credentials, revoked-ID ownership records, account fences and indexes remain counted and nonevictable. The fixture runtime role cannot truncate, and its DELETE policy permits ceremony rows only.

Known COMMITTED acknowledgements retain their required validation timing even after a late acknowledgement; optional completion sampling is absent. UNKNOWN carries no timing and is never automatically retried or rescued from a matching row. Core normal service release needs its fresh final root admission check; raw permanent-only reseal returns factual receipt truth. The store checks primary durability settings and uses transaction-local `synchronous_commit=on`. The application separately owns SQL writer exclusion, closed complete inventory/codec/capacity preflight, trusted witness admission, connection pooling, key lifecycle and restore custody. While that listener remains up, the runner stops its PostgreSQL primary: browser sessions, MCP and introspection report service unavailability instead of invalid credentials, and the token endpoint releases no credential. Returning the same primary on a fixed run-local loopback port restores admission of the original token. Reusing the code then releases no new credentials and revokes that grant; the live MCP listener and a third JVM both observe the revocation. This is a local HTTP integration check, not an independent browser qualification. The probe acquires JDBC connections for Pyranid; all store SQL and transactions stay in Pyranid. Its fixture connection source and ephemeral file keys do not qualify a production pool, managed key lifecycle, cross-host session recovery or admission after backup restore.


### Durable SCIM PATCH qualification

`PostgresqlScimPatch` implements the deliberately narrow storage profile documented in the [SCIM provisioning guide](../../docs/scim-provisioning.md). [ScimStoreProbe](src/test/java/example/pending/ScimStoreProbe.java) and [run_scim.py](run_scim.py) qualify that compiled recipe against the reviewed PostgreSQL image in [the SCIM runtime pins](../../interop/scim/pins.json). Cache that exact image first; the runner uses `--pull=never`.

The fixture binds its database only to host loopback, uses a disposable credential and owned volume, and compiles the recipe/probe for Java 17 with warnings fatal. It verifies attempted-path authorization for no-ops, denied and late-failing PATCH atomicity, stale versions, application uniqueness/member-reference/profile checks, ordered Group membership and authoritative metadata. A statement fault happens after an actual first member INSERT and proves the resource row and all membership changes roll back together. A separate fault happens after an actual COMMIT, proves the write reached PostgreSQL, and requires `Unknown` with no success response or automatic replay. Two independent JVMs race the same version and produce one commit and one 412. Output-cap rejection precedes persistence; an actual stopped primary is unavailable, and a new JVM after restart reads the persisted resource, ordered members and version. Repeated clear on the canonical empty-membership profile preserves the version.
