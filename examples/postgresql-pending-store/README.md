# PostgreSQL storage examples

These application-side examples implement PostgreSQL storage for OAuth and OIDC flows that can reach different JVMs. They use Pyranid 4.7.0 for bound SQL and transaction lifecycle against one authoritative primary. The Revetsec core artifact retains zero runtime dependencies.

Apply `schema.sql` with your migration tool, then create one clock row for a **new** stable namespace. Pass the same namespace and database to every JVM. For example:

```java
var store = new PostgresqlPendingAuthorizationStore(
    "my_application", connectionSource, 1_024, 8 * 1_024, 4L * 1_024 * 1_024);
```

`connectionSource.open(remaining)` is application-owned and thread-safe. It must bound pool acquisition, DNS and connection setup by the shrinking budget, return a distinct logical connection to the authoritative primary for each call, and preserve the normal PostgreSQL TLS/certificate policy. The example sets a driver network timeout and a transaction-local statement timeout for subsequent SQL. Connection sources that can block without honoring `remaining` do not meet the `PendingAuthorizationStore` contract.

The example caps one database operation at one minute even if a caller supplies a longer budget. It never extends a shorter caller budget.

Every operation locks the namespace clock row. It stores the largest observed database instant, so an observed backward clock step cannot revive an expired record. Save prunes expired rows, rejects a duplicate live key and refuses capacity without evicting live logins. Consume removes once across JVMs. The browser binding and state are hashed for the table key; the opaque record is stored as plaintext and contains sensitive pending authorization data, so applications must protect database access, transport, backups and logs.

The result is released only after Pyranid reports a confirmed COMMITTED transaction. A failed or uncertain commit produces a fixed storage failure; callers must not automatically retry a callback or treat an uncertain save as successful. The local fixture injects a lost COMMIT acknowledgement after the database commit and verifies both application boundaries: the save path withholds its redirect, and the callback path withholds tokens and makes no token request. A consumed record may be lost under an uncertain commit, requiring a new login. The application owns database credentials, capacity settings, migrations, monitoring, backups and restore admission. A restored snapshot can restore an authentically consumed record and an older clock fence; keep routes closed until the application's external recovery fence and key procedure are complete. This source does not establish high availability, cross-host failover or power-loss durability on its own.

## Optional shared CIMD metadata cache

The companion `PostgresqlClientMetadataCache` implements `OAuthClientMetadataCache` for compatible authorization-server nodes. Apply the `cimd_cache_*` tables in `schema.sql`, provision a new stable cache namespace, and select it through `OAuthClientMetadataPolicy.Builder.cache(...)`. The cache uses Pyranid-managed transactions and oldest-write-first eviction, capped at the configured entry count. Its application-supplied connection source must bound acquisition and return clean, distinct connections to the same primary. This optional cache never replaces the authoritative authorization-server store or pending-authorization store.

It persists Revetsec's bounded encrypted carriers exactly. Revetsec still authenticates and evaluates each hit under current issuer, client, policy and freshness rules; each credential transition still requires its own successful fresh metadata fetch. An expired carrier can remain in storage until eviction and is not permission to use the document. A failed or uncertain cache write reports a fixed failure, which may require a read to reconcile; the caller must not treat it as a successful compare-and-set. A database outage is a failure, not a confirmed miss. Cache restoration, eviction and node changes cannot turn a carrier into a credential or a fresh-fetch proof. This example demonstrates one PostgreSQL primary and independent JVMs on one host, not cross-host high availability.

## Optional authoritative issuer store

`PostgresqlIssuerStore` implements the application-owned `OAuthAuthorizationServerStore` for a shared issuer. Apply the `issuer_store_*` tables in `schema.sql`, provision a stable namespace before the issuer's first initialization, and configure every issuer JVM with the same namespace and primary:

```java
var issuerStore = new PostgresqlIssuerStore("my_issuer", connectionSource, 100_000);
// Supply issuerStore to OAuthAuthorizationServer.Builder.store(...).
```

All three storage examples use Pyranid 4.7.0 for bound SQL and transaction completion. Pyranid and the PostgreSQL driver remain application dependencies and do not enter Revetsec core. The issuer store's connection source must open a clean, distinct primary connection within the supplied remaining budget, including pool acquisition and connection setup; normal deployments must preserve their PostgreSQL TLS and certificate policy. The store requires an actual primary with `fsync` and `full_page_writes` enabled and sets transaction-local `synchronous_commit=on`.

Every read and commit locks the provisioned namespace row. A commit compares the entire engine-provided read set, including confirmed absence, before applying its mutations. A predicate conflict has zero effects; a lost COMMIT acknowledgement returns `UNKNOWN` even if the database applied the write. The application must reconcile that outcome before repeating a non-idempotent operation. Entries are never automatically evicted: capacity refusal is safer than dropping an active grant, replay tombstone or permanent issuer/subject fence. Any operator cleanup must obey the same namespace lock and Revetsec retention horizon. Keep issuer routes closed during restore until the application's external recovery fence and key procedure establish safe admission.

The local probe uses ephemeral keys and a fixed synthetic clock. It checks fresh initialization, cross-JVM code issuance and redemption, atomic two-JVM code and refresh races, grant invalidation on credential reuse, isolation of another grant, cross-JVM refresh rotation, online token status, a closed issuer read during database outage, persistence of live and revoked grants across a PostgreSQL restart, and global revocation. A held PostgreSQL namespace lock makes short-budget token status and global revocation fail promptly; releasing it leaves the existing grant active. The probe also checks that lowering the configured capacity refuses new issuance without evicting an existing grant or breaking a condition-only status read. In a separate fixture namespace, removal of a permanent subject fence causes an established grant's status check to fail closed while the unaffected namespace remains available. Never remove such a fence in a deployment or call fresh initialization to repair it.

Uncertain initialization, code redemption, refresh and subject-revocation COMMIT outcomes are reported without claiming success. Uncertain token commits withhold credentials; separate JVMs observe the committed code consumption or refresh rotation by rejecting reuse. After the fixture's uncertain subject revocation, a separate JVM observes its prior grant inactive; a new grant in the advanced subject epoch is then active until another confirmed subject revocation. An inactive token alone is not a general operator reconciliation procedure or permission to repeat an epoch advance. This is one-host, one-primary evidence; it does not qualify cross-host failover, power-loss durability, a production connection pool or an application restore procedure.

`run.py` compiles the example with warning-fatal Java 17 settings and exercises duplicate, expiry, capacity, rollback fencing, browser binding, cross-JVM single use, lock timeout, database outage and restart against a cached disposable PostgreSQL image. A loopback-only synthetic token endpoint checks the authorization-code form and persisted PKCE verifier: a valid callback redeems once, replay and wrong-browser binding send no token request, and simultaneous callbacks in two JVMs produce exactly one redemption.

The OIDC lanes verify cross-JVM identity release, wrong-nonce and bad-signature rejection, and one winner in callback races. The HMAC lane explicitly opts into Revetsec's compatibility mode with a run-local secret. The RS256 lane generates a fresh key pair inside a test JVM and serves its public JWKS from the loopback provider; the private key is never written to disk or included in the runner output. These are local protocol fixtures, not real-provider or cross-host qualification.

The runner also checks cross-JVM cache reads and compare-and-set races, bounded eviction, uncertain COMMIT, confirmed reads despite a connection-close acknowledgement failure, outage and restart. It requires absolute paths to a current core JAR, Java home, and the pinned Pyranid, PostgreSQL, JSpecify and JSR-305 JARs; run `python3 run.py --help` for the arguments. Docker resources, the local endpoint and test credentials are removed after the run.

To include the self-issued Soklet application lane, also pass `--adapter-jar` for the matching Revetsec/Soklet helper and `--framework-jar` for the pinned Soklet 4.0.0 JAR. The runner compiles the current app source with the Pyranid store, then runs fresh and established application instances in separate JVMs against a dedicated PostgreSQL namespace. It checks an issued token across startup, refusal to reinitialize an established issuer, rejection with the wrong sealing key and refresh rotation across JVMs. An established Soklet process then serves OAuth metadata and JWKS over an actual loopback HTTP listener, returns an active introspection verdict, and accepts the persisted token on its MCP listener while denying a missing bearer. Refresh replay in another JVM revokes that token; the still-running Soklet process rejects its next MCP call and returns an inactive introspection verdict.

The fixture's application-owned key provider reads an atomic generation marker from its private temporary directory. During a live Soklet process, the runner changes from the initial RSA signing key to a second ephemeral key while retaining the first public key through a declared retirement boundary. It verifies overlapping JWKS publication, new-key signing, continued old-token admission, and new-token admission from another JVM. An attempted removal of the old public key before that boundary makes JWKS and protected-resource admission unavailable; restoring the retained-key snapshot restores admission. This exercises Revetsec's observed lifecycle guard, not durable key distribution: an application must persist the generation, publication and retirement history and publish changes to all nodes before advancing its provider.

A scripted HTTP client also completes the app's login and consent forms on the first established Soklet process. The runner stops that process before redeeming its issued code, starts another established process with the same keys and store, checks that the old browser cookie is gone, and redeems the code at the actual token endpoint. The resulting token reaches the restarted MCP listener. While that listener remains up, the runner stops its PostgreSQL primary: MCP and introspection report service unavailability instead of invalid credentials, and the token endpoint releases no credential. Returning the same primary on a fixed run-local loopback port restores admission of the original token. Reusing the code then releases no new credentials and revokes that grant; the live MCP listener and a third JVM both observe the revocation. This is a local HTTP integration check, not an independent browser qualification. The probe acquires JDBC connections for Pyranid; all store SQL and transactions stay in Pyranid. Its fixture connection source and ephemeral file keys do not qualify a production pool, managed key lifecycle, browser-session recovery or admission after backup restore.
