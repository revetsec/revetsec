How:
- Each container ran with --network none, ISSUER=https://localhost:3000, and the test CA's TLS server certificate and
  key from src/test/resources/tls/. The server.js described below was copied in before the container started.
- A capture driver (Python standard library, adapted from interop/spike/oidc_smoke.py) ran in a second container that
  shared the provider container's network namespace, so every request stayed on that namespace's loopback.
- For each test client it ran the authorization-code flow with PKCE (S256) through server.js's auto-login handler,
  which logs in the synthetic test account, and exchanged the code at the token endpoint with client_secret_basic.
- It fetched each key set before and after the flows; both fetches returned the same bytes. The files hold each
  response body byte for byte as served, with no line break added.

Runs:
- default (files default-*): interop/node-oidc-provider/server.js, unmodified. It generates an RS256 and an ES256 key
  at start, and its one client gets ID tokens signed RS256, oidc-provider's default.
- algorithms (files algorithms-*): the same server.js with two changes. signingKeys() generates RSA keys with alg
  RS256, RS384, RS512, PS256, PS384 and PS512 (2048, 3072 and 4096 bits for the 256, 384 and 512 variants), EC keys
  with alg ES256, ES384 and ES512 on P-256, P-384 and P-521, one Ed25519 key with no alg (oidc-provider then signs both
  Ed25519 and EdDSA with it), and one ML-DSA-44 key (kty AKP). And there is one client per ID token signing algorithm,
  revetsec-test-client-<alg>, with enabledJWA.idTokenSigningAlgValues naming those twelve algorithms. Client secret,
  redirect URIs and test account are those of server.js.
