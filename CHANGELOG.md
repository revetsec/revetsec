# Changelog

All notable changes to Revetsec are recorded in this file.

Each release gets a `## X.Y.Z (YYYY-MM-DD)` heading with Added, Changed, Fixed, Security and Migration Notes sections as needed. A released security fix names its GHSA or CVE ID when assigned; pre-release hardening without an advisory names its review. Changes that reject previously accepted insecure input, or that remove an algorithm from a default, are listed under Security (see the security-tightening policy in [COMPATIBILITY.md](COMPATIBILITY.md)).

## 1.0.0 (2026-11-13)

### Changed
- OIDC refresh naming now follows the library's value/result convention: `OidcRefresh` is the checked success value, while sealed `OidcRefreshResult` carries `Succeeded`, local `Rejected` and `RejectedEndpoint` outcomes. `Succeeded.getRefresh()` releases the value. The former `OidcRefreshOutcome` name and `getRefreshResult()` accessor are removed before 1.0.
- Public numeric limits, parameters and returns use non-null boxed types consistently; the public-API contract now rejects primitive fields, parameters and value returns other than `equals`/`hashCode`. This is an intentional pre-1.0 source/binary signature change.
- `WebAuthnRelyingParty.completeReauthenticationResult` now returns a restricted five-outcome `WebAuthnReauthenticationResult` rather than the general authentication result. Only success releases an account/RP/credential/action/ceremony-bound proof; applications match the ceremony to their original pending action and still authorize and consume that one-use action. The general authentication completion API is unchanged. This is an intentional pre-1.0 source and binary signature change.
- The complete Soklet Playground now selects a restrictive SCIM service-client directory with explicit alpha/beta tenant roles, field/query policies, exact write versions and bounded Argon2id work. Canonical tenant paths retain an alpha alias; custom SCIM base settings refuse explicitly. The earlier administrative interoperability fixture remains separate. See the [service-client profile](docs/scim-restrictive-service-clients.md).
- `RevetsecException.isTemporaryCondition()` replaces `isTransient()` without an alias. Fixed classifications and serialized fields remain unchanged; neither flag value grants replay permission or establishes whether earlier work had effects. See the [operation effect matrix](docs/failure-effects.md).
- The issuer signing-key factory is now `OAuthIssuerSigningKey.fromRsaKeyPair`, with no `fromKeyPair` alias. The issuer remains RS256-only; general signing and client-assertion factories retain their names. This is an intentional pre-1.0 source change.
- TOTP provisioning limits the final percent-encoded `otpauth` URI to 512 ASCII bytes. Display labels reject colons, controls, Unicode format/separator characters and boundary whitespace; accepted text is retained without normalization or truncation. See [provisioning bounds](docs/totp-recovery.md).
- OIDC request preferences now use ordered `acrPreferences` separately from local `requiredAcrValues` acceptance. Genuine session references retain each login's effective acceptance set for refresh. Session-reference storage is version 2; old version-1 references and embedded logout hints are rejected and require authentication again. See [flow assurance and migration](docs/oidc-flow-assurance.md).
- The Okta SCIM preset now ignores supplied read-only `display` only in standard Group member object merges, preserving server metadata and attempted paths. Strict/Entra/custom/direct writes and other protected fields retain their rules. Multivalue ADD identity excludes hidden values; wholly hidden multivalue ADD and immutable hidden duplicate echoes refuse. Nested extension child names cannot use colons to retarget another registered schema.
- The shared `ScimResourceType.userInstance()` registration contains only the core User schema. Applications supporting Enterprise User attributes must register `ScimSchema.enterpriseUserInstance()` explicitly through `schemaExtensions(...)`; the provisioning guide shows optional and required extension selection.
- Standardized JOSE key API names on `Jwk` and `Jwks`, with `JwksSource`, `StaticJwksSource` and `RemoteJwksSource`.
  Related builders, endpoint methods, observer hooks and internal helpers use the same acronyms.

- TOTP, WebAuthn and OAuth issuer stores now return coherent admitted-time observations and contextual commit receipts. Timed stateful operations use immutable namespace/issuer minima, authenticated entity floors and temporal predicates checked with fresh authority time after lock waits. Worker clocks are health inputs rather than a shared-time fallback; independent entities do not advance a common clock root on normal traffic. Existing issuer/subject emergency epoch revocation retains its separate fence-only admission under current recovery control. See the [shared-clock store and consumer contract](docs/shared-clock-stores.md).
- Stateful service results distinguish definitely unperformed work, uncertain mutation and known commitment requiring reconciliation. Withheld proof or credential output does not undo an applied transition; raw initialization/reseal receipts acknowledge effects without opening serving admission.

### Added
- Application-integrated OAuth authorization-server operations: browser authorization and consent, authorization-code exchange, refresh rotation, grant/token revocation, resource-only introspection, online access-token status, metadata and public JWKS responses. The public builder exposes the bounded settings; `OAuthServerResponse` retains explicit credential emission and redacted diagnostics. Applications supply users, authentication, consent, grant policy, keys and authoritative atomic storage. See the [issuer application contracts](docs/oauth-server-application-contracts.md).
- Opt-in client-ID metadata documents (CIMD), integrated with registered-client selection and fresh code/refresh admission. Address selection and HTTP/TLS transport pin the numeric peer while preserving hostname verification, bounded chain construction and response parsing. Exact registrations are checked first, and source-separated security fingerprints bind consent and grants. Metadata scopes remain untrusted and require application approval. Cache reuse follows authenticated source binding and conservative freshness; the application explicitly selects an `OAuthClientMetadataCache`, including the bounded `InMemoryOAuthClientMetadataCache` option. The storage SPI does not qualify a shared cache deployment by itself.
- An unpublished self-issued Soklet MCP example with app-owned login/consent, bounded volatile storage, issuance and online revocation checks, plus OIDC, passkey, TOTP and PostgreSQL integration examples. The local examples retain their documented state, session and recovery limitations; see [runnable examples](examples/README.md).
- OAuth and OpenID Connect client operations with browser-bound pending state, PKCE S256, raw callback parsing, checked identity results, refresh and UserInfo. Added the explicit Microsoft Entra common/organizations issuer policy with signature-verified tenant decisions and tenant-bound UserInfo/refresh checks. Hosted Entra acceptance remains unproven. See the [OAuth client guide](docs/oauth-client.md) and [issuer policy](docs/oidc-issuer-policy.md).
- RP-Initiated OIDC Logout core: trusted end-session metadata, explicit original-reference-bound ID-token-hint lifecycle, typed pending storage, GET/form POST preparation and correlation-only returns. Local POST/CSRF authorization and session termination precede preparation. See the [logout guide](docs/oidc-logout.md); application/carrier and provider/browser qualification remain open.
- WebAuthn relying-party registration, discoverable sign-in, account-pinned reauthentication and credential management, with authoritative conditional credential transitions and explicit recovery admission. Exact configured HTTPS origins may use the RP host or a dot-delimited child host; an eligible host is not wildcard trust. See the [browser/extension policy](docs/webauthn-browser-compatibility.md) and [passkey example](examples/passkeys-soklet/README.md).
- TOTP authenticator enrollment/confirmation, factor replacement/removal, replay-protected verification and one-use recovery-code batches, using epoch-fenced atomic state and application-owned recovery admission. See the [TOTP and recovery guide](docs/totp-recovery.md).
- Bounded Argon2id password hashing, native verifier checks, optional pepper policy and explicit bcrypt/PBKDF2 legacy verification. Applications select shared local work admission and retain account/password/session policy. See the [password hashing guide](docs/password-hashing.md).
- Standalone public verification-key/JWKS publication through `PublishedJwk` and `JwksPublisher`, including bounded public projections and prepared HTTP responses; see the [JWKS publication guide](docs/jwks-publication.md).
- HTTP-POST SAML Single Logout in both directions, with exact-root XML signatures, strict logout semantics and a shared atomic replay domain across POST and Redirect. Added explicit POST endpoints and metadata, logout form parsing/results, Soklet and Servlet transport helpers, and local interoperability fixtures. See the [SAML service provider (SP) guide](docs/saml-sp.md).
- SCIM registered schemas and immutable resources, create/PUT validation, schema-bound filter policies, GET/SearchRequest queries, projection, index/cursor page framing, conditional headers, discovery and bounded response preparation. Ordered atomic PATCH and conservative membership reduction include explicit string matching, attempted/effective/supplied paths and PATCH response policy. The optional `ScimFilterEvaluator` evaluates a policy-approved filter against one resource; applications own collection retrieval, authorization and persistence. See [SCIM server primitives](docs/scim-server-primitives.md).
- Bounded SCIM filter and attribute-path syntax parsing with sealed results and fixed errors, an immutable six-kind AST, a Java 17 visitor, explicit serialization and default-deny policy configuration. Syntax success grants no query permission; the provider binds schemas and enforces complete policies. See [SCIM filter syntax](docs/scim-filters.md).

#### Earlier pre-release milestones

These entries describe their original implementation stage. Their type counts and test inventories are historical snapshots, not the current API inventory or current-source qualification.

- Defined a private-key client test profile: exact registered public JWKS and raw assertion checks, with explicit unsupported-profile exclusions and the suite's mandatory Basic exception.
- Local private-key integration checks against pinned Keycloak 26.7.4 and node-oidc-provider 9.12.2: independent registrations, RS256/RS384/PS256, both audiences, all POST roles and wrong-key/algorithm rejection. Keycloak revocation in endpoint audience mode is a documented provider limitation.

- Generated OAuth `private_key_jwt` assertions: immutable rotating key snapshots, per-role metadata, issuer or explicit endpoint audiences, original operation deadlines and preparation failure observation.

- Bounded import-only `KeyImports`: certificates, SPKI, PKCS#8 and two-prime RSA PKCS#1 in the selected RSA/P-256/P-384/Ed25519 profiles, with fixed input ceilings and a separate budgeted pair check. No key generation/export or certificate trust engine.
- Shared signing (`JwsSigner`): PS256/PS384/PS512/RS256/RS384/RS512, ES256/P-256, ES384/P-384 and pure Ed25519, checked public-key snapshots, exact bounded JSON claims and pair verification before credential output. Explicit `warmUp` performs a noncredential probe; factories perform no signing. Opaque application-owned private keys are retained without export. Fixed `JwsSigningException` reasons distinguish provider unavailability, pair mismatch and exhausted budgets. OAuth client assertions use the six RSA profiles, ES256/ES384 and fully specified Ed25519; issuer signing remains RS256. ES512 and legacy EdDSA remain verification-only.

- JOSE (milestone M2): verification of signed JWTs against JSON Web Key Sets.
  - `com.revetsec.jose`, 16 public types:
    - `JwtValidator`: validates a JWT in the JWS compact serialization for one issuer. By default it allows RS256 alone, `typ` absent or `JWT`, 60 s of clock skew and tokens up to 64 KiB, and requires `iss`, `exp` and an expected audience. It never accepts `none`, an HMAC algorithm, a key or key URL in the header (`jwk`, `jku`, `x5u`), `crit`, `b64`, `zip`, `cty`, an encrypted or JSON-serialized token, or a token with a `cnf` claim. A malformed signature is refused before any key is looked up;
    - `Jwt` and `JwtClaims`: the validated token and its claims, which only validation creates;
    - `JwsAlgorithm`: RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512, Ed25519 and EdDSA, plus HS256, HS384 and HS512, which `JwtValidator` refuses;
    - `Jwks`, `Jwk` and `JwkSkipReason`: a key set keeps only usable public verification keys and skips the rest with one of 13 reasons. RSA keys are 2,048 to 16,384 bits, with an odd, minimal modulus, an odd public exponent of at least 65,537 and no ROCA fingerprint; EC keys lie on P-256, P-384 or P-521; Ed25519 keys decode to a point of more than small order. An RSA key without `alg` serves only a sole allowed RSA algorithm, and a key's `issuer` member binds it to that issuer, with one exception for Microsoft Entra ID's `{tenantid}` template;
    - `JwksSource`, `StaticJwksSource` and `RemoteJwksSource`: keys the application holds, or a key set fetched lazily on the caller's thread and cached by `Cache-Control` and `Expires` within 1 minute and 6 hours by default. An unknown key refreshes it at most once per cooldown, failures back off from 30 s to 5 minutes at the defaults without resetting on success, at most two requests start per cooldown, which may not be longer than the minimum time to live, and stale keys are served for a bounded time while refreshes fail;
    - `JoseObserver`, with nine hooks; `JoseException`, sealed, with one shared `Reason` and three subclasses, `MalformedJoseInputException`, `UnsupportedJoseFeatureException` and `JwtValidationException`; and `JwksUnavailableException`, whose category says why a key set could not be had.
  - `OutboundUriPolicy.publicAddressesOnlyInstance()`: permits only globally reachable addresses and DNS names outside the local and special-use names it lists.
  - Compatibility modes, the first two: `acceptAnyAudience(true)` and `acknowledgeUnpatchedRuntime(true)`.
  - Internal, not API: signature verification by curve and hash, with the ECDSA shape and range check, DER encoding, EC on-curve checks, the RSA key policy, Ed25519 point decoding and HMAC-SHA-384 and -512; compact JWS parsing, the header and claims policies and key selection; the RFC 9111 cache lifetime and HTTP dates; and one URI check shared by build time and request time.
  - Tests: 28 Wycheproof test-vector files, vendored at a pinned commit with a SHA-256 manifest and run against per-vector expectation manifests; the examples of RFC 7515, 7517, 7520 and 8037, and the test vectors of RFC 8032 and RFC 4231; Microsoft Entra ID's key sets as read on 2026-09-27; key sets and tokens captured from local Keycloak and node-oidc-provider test containers, replayed offline; hostile key-set endpoints, including ones that always fail, alternate with valid key sets or never answer; Jazzer fuzz targets for compact JWS parsing, JSON Web Keys, `JwtValidator`, ECDSA signatures and cache lifetimes; new source-policy rules; and a check that every threat-model invariant cites the tests or build checks that enforce it.
  - Build: coverage floors for `jose` and `internal.jose`, and the other floors re-measured; PIT targets for `jose`, `internal.jose` and the new signature and key classes; larger ClusterFuzzLite budgets; and packaged consumers that call the `jose` API.
- Foundations (milestone M1, before protocol implementation):
  - `com.revetsec`:
    - `RevetsecException` and `ErrorCategory`: the root of Revetsec's exceptions, each with a category, an indication of a temporary condition derived from the category and cause, a fixed message, and suppression disabled;
    - `StateSealer`, `SealingKey` and `InvalidSealedStateException`: short strings sealed with AES-256-GCM under a per-value key derived with HKDF-SHA256, bound to a context and a lifetime, with key IDs for rotation and one exception for every failure to open;
    - `OutboundUriPolicy`: classifies IP address literals, and never resolves hostnames.
  - `com.revetsec.json`: an immutable JSON value model, `JsonValue` and its six permitted types plus `JsonObject.Builder`, with redacted `toString()`, equality by numeric value for numbers, and a depth limit of 64.
  - Internal, not API:
    - a strict JSON parser ported from Soklet's codec, with per-profile limits, and RFC 7638 thumbprint input;
    - strict Base64, base64url, percent, form and UTF-8 codecs, and PEM parsing;
    - HKDF and the sealer's format;
    - a bounded HTTP exchange on the JDK `HttpClient`, with deadlines, size limits, and rejection of redirects, content encodings, framing anomalies and unexpected media types, plus a lazily created default client;
    - the resource-limits registry and contained observer dispatch.
  - Tests: the JSONTestSuite parsing files, vendored at a pinned commit with a SHA-256 manifest; a catalog of hostile HTTP responses; known-answer and tamper tests for the sealer; Jazzer fuzz targets for the JSON codec and model, RFC 7638, the sealer, PEM and the encoders, in place of M0's placeholder target; and new source-policy rules.
  - Build: a Javadoc CI job on a checksum-pinned JDK 26 with every doclint group except `html`; a Gradle consumer next to the Maven one in the packaged-consumer check, both calling the public API; and coverage floors set from measured runs.
- Repository scaffold (milestone M0, before protocol implementation):
  - a single-module Maven build for `com.revetsec:revetsec`, targeting Java 17, that fails if any compile or runtime dependency is declared;
  - placeholder packages;
  - contract tests for public API shape, package dependencies, source policy and documentation wording;
  - CI workflows, a fuzzing skeleton, and a test-only certificate authority;
  - the repository documents: README, COMPATIBILITY, SECURITY, CONTRIBUTING, NAMING_CONVENTIONS, NOTICE, and skeletons under `docs/`.

### Security
- Checked WebAuthn reauthentication now snapshots the caller's expected account handle before invoking an external store and wipes the snapshot afterward. A callback can no longer mutate the caller-owned byte array to change the post-commit account comparison; ceremony consumption and the typed checked rejection remain preserved.
- Review `3.jose-oauth-and-oidc.6`: returned refresh ID tokens must satisfy the original flow's ACR acceptance policy rather than a different client default.

- Pre-release hardening following the October security reviews includes caller-cancellation isolation across shared caches, token-specific introspection error handling, rejected injected HTTP authenticators/cookie handlers, and bounded client-metadata admission, TLS chain construction, HTTP status classification and cache recovery. The shared-time transition above supersedes the earlier issuer clock-reservation design.
- WebAuthn ceremony expiry, atomic consumption and proof release use admitted store time and final recovery/time admission. Ordinary reads, barriers and no-effect refusals do not reclaim retained ceremonies or advance floors; finite capacity can still refuse safely. Late known ceremony commits require reconciliation, while unknown writes release no proof. Account- and purpose-bound reauthentication, canonical registration `credProtect`, malformed-signature rejection and permanent-record reseal remain explicit boundaries.
- SAML text attributes remain visible under mutable unsigned namespace declarations; replay admission is partitioned by connection. SCIM trusted resource construction and delegated string matching obey configured work limits. The Servlet and Soklet adapters validate credential-bearing redirects before writing responses.
- Playground logout callbacks preserve live pending state and cookies on invalid input, clearing them after verified terminal status or expiry. Logout completion reports `Indeterminate` for failures after confirmed pending-store consumption, including revalidation and replay-admission failures.
- Signed but semantically invalid POST and Redirect logout responses no longer consume pending state. Logout requires conditional atomic pending-store consumption after document validation and authenticated pending binding/correlation checks; legacy custom stores fail closed until they implement `consumeIfMatches`.
- Logout replay retention spans all supported age/skew policies for both POST and Redirect requests and responses. Local message-validity checks remain unchanged; a policy increase or mixed-policy deployment cannot re-admit a previously accepted message after a narrower-policy cache entry expires.

The earlier outbound-policy tightening below rejects input accepted by the initial foundation milestone. It was never released.

- `OutboundUriPolicy.defaultInstance()` also rejects more of the cloud metadata endpoints known as of 2026-09-27 (100.100.100.200, 168.63.129.16, fd00:ec2::23 and fd20:ce::254, and the names `metadata.google.internal` and `metadata.goog` and every name under them), the RFC 8215 local-use NAT64 prefix 64:ff9b:1::/48, and IPv4-translated literals around a rejected IPv4 address.

### Migration Notes
- Clear version-1 OIDC session references and old logout hints containing them before adopting the version-2 flow-policy format, then require authentication again. An unchanged sealer purpose does not upgrade the inner stored payload; do not infer the missing per-flow acceptance set from current defaults.

- Update TOTP, WebAuthn and issuer stores, wrappers, consumers and result handling together. The pre-1.0 store APIs, time/commit carriers and persisted formats require a coordinated transition; compiling new interfaces does not migrate an established namespace. Normal readers do not promote legacy records. See the [store/consumer contract](docs/shared-clock-stores.md) and [closed migration/restore fixture](verification/shared-clock-migration/README.md).
- Migration/restore keeps serving admission closed, excludes old writers and preserves every retained charge, replay record, ownership tombstone, floor and permanent fence. A structurally completed fixture is not deployment activation: actual trusted time, writer fencing, capacity and external recovery admission require the application's qualified profile.
- Custom SAML pending stores must implement conditional atomic `consumeIfMatches`; legacy implementations fail closed. Deploy the updated readers before accepting the larger documented pending/session-reference forms, and keep application-owned trusted storage when a value cannot fit the selected sealing budget. See the [SAML SP guide](docs/saml-sp.md).

### Selected application and qualification work still open

The following selected work still requires application integration and qualification:

- RP-Initiated OIDC Logout local-first application recipe and framework/container/browser/provider joins. The core hint/request/return APIs are implemented; local session termination remains app-owned.
- Final application/current-candidate/browser qualification for Google Identity Services and Sign in with Apple backend-token recipes. Common Java 17, paired Servlet containers and pinned Soklet local components now have evidence. The pinned Soklet profile requires a qualified trusted HTTPS edge that rejects every raw query-bearing target, including a bare question mark, before framework parsing.

Implemented APIs and local fixtures do not close the remaining current-source review, provider/browser, durable recovery or release qualification.
