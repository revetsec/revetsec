# Changelog

All notable changes to Revetsec are recorded in this file.

Each release gets a `## X.Y.Z (YYYY-MM-DD)` heading with Added, Changed, Fixed, Security and Migration Notes sections as needed. A released security fix names its GHSA or CVE ID when assigned; pre-release hardening without an advisory names its review. Changes that reject previously accepted insecure input, or that remove an algorithm from a default, are listed under Security (see the security-tightening policy in [COMPATIBILITY.md](COMPATIBILITY.md)).

## 1.0.0 (2026-11-15)

First release.

### Added
- Foundations: `RevetsecException` with a fixed category, message and temporary-condition flag (neither flag value grants replay permission; see the [operation effect matrix](docs/failure-effects.md)); `StateSealer` for short values sealed with AES-256-GCM, bound to a context and a lifetime, with key IDs for rotation (see the [sealing-key lifecycle](docs/sealing-key-lifecycle.md)); an immutable JSON value model; and `OutboundUriPolicy`, which classifies outbound addresses without resolving hostnames.
- JWT and JWS verification: `JwtValidator` checks compact-serialization JWTs for one issuer against keys from `StaticJwksSource` or the lazily fetched, bounded-cache `RemoteJwksSource`. Algorithms come only from the validator's allowlist (RS256 by default); `none`, HMAC, header-supplied keys and key URLs, `crit`, `b64`, `zip`, and encrypted or JSON-serialized tokens are refused. A key set keeps only usable public keys and reports why each other key was skipped. See [supported algorithms](docs/supported-algorithms.md).
- Bounded signing through `JwsSigner`: PS256/PS384/PS512, RS256/RS384/RS512, ES256 on P-256, ES384 on P-384 and pure Ed25519, with checked public-key snapshots, exact bounded JSON claims and a key-pair check before any credential is produced. Application-owned private keys are never exported. Standalone public-key and JWKS publication uses `PublishedJwk` and `JwksPublisher`; see the [JWKS publication guide](docs/jwks-publication.md).
- Import-only `KeyImports` for certificates, SPKI, PKCS#8 and two-prime RSA PKCS#1 keys in the RSA, P-256, P-384 and Ed25519 profiles, with fixed input limits and a separately budgeted pair check. There is no key generation, private-key export or certificate trust engine. See [bounded key imports](docs/key-imports.md).
- OAuth and OpenID Connect client operations with browser-bound pending state, PKCE S256, raw callback parsing, checked identity results, refresh and UserInfo. Client authentication includes `private_key_jwt` assertions from rotating key snapshots, using the six RSA profiles, ES256/ES384 or Ed25519. OIDC separates ordered `acrPreferences` from the local `requiredAcrValues` acceptance set, and refresh keeps each login's acceptance set; see [flow assurance](docs/oidc-flow-assurance.md). The explicit Microsoft Entra common/organizations issuer policy uses signature-verified tenant decisions and tenant-bound UserInfo/refresh checks; hosted Entra acceptance remains unproven. See the [OAuth client guide](docs/oauth-client.md) and [issuer policy](docs/oidc-issuer-policy.md).
- Resource-server access-token validation: `JwtAccessTokenValidator` for RFC 9068 JWT access tokens and `TokenIntrospectionClient` for RFC 7662 introspection, both returning sealed `AccessTokenValidator` results. Introspection caches no credential result. Its endpoint backoff opens immediately on HTTP 401/429, and after three transport or 5xx failures in one cooldown window. See [resource-server validation](README.md#resource-server-validation).
- RP-Initiated OIDC Logout: trusted end-session metadata, an explicit ID-token-hint lifecycle bound to the original session reference, typed pending storage, GET/form POST preparation and correlation-only returns. Local POST/CSRF authorization and session termination remain application-owned and come first. See the [logout guide](docs/oidc-logout.md).
- Application-integrated OAuth authorization-server operations: browser authorization and consent, authorization-code exchange, refresh rotation, grant/token revocation, resource-only introspection, online access-token status, metadata and public JWKS responses. The issuer signs RS256 access tokens with a key from `OAuthIssuerSigningKey.fromRsaKeyPair`. Applications supply users, authentication, consent, grant policy, keys and authoritative atomic storage. See the [issuer application contracts](docs/oauth-server-application-contracts.md).
- Opt-in client-ID metadata documents (CIMD), integrated with registered-client selection and fresh code/refresh admission. Address selection and HTTP/TLS transport pin the numeric peer while preserving hostname verification, bounded chain construction and response parsing. Exact registrations are checked first, and source-separated security fingerprints bind consent and grants. Metadata scopes remain untrusted and require application approval. The application explicitly selects an `OAuthClientMetadataCache`, including the bounded `InMemoryOAuthClientMetadataCache`; the storage SPI does not qualify a shared cache deployment by itself.
- WebAuthn relying-party registration, discoverable sign-in, account-pinned reauthentication and credential management, with authoritative conditional credential transitions and explicit recovery admission. Reauthentication returns its own restricted `WebAuthnReauthenticationResult`; only success releases an account-, credential- and action-bound proof. Registration exposes and persists display-only AAGUID and backup flags, and successful sign-in and reauthentication expose the committed backup flags. Exact configured HTTPS origins may use the RP host or a dot-delimited child host; an eligible host is not wildcard trust. See the [browser/extension policy](docs/webauthn-browser-compatibility.md) and [passkey example](examples/passkeys-soklet/README.md).
- TOTP authenticator enrollment and confirmation, factor replacement and removal, replay-protected verification and one-use recovery-code batches, using epoch-fenced atomic state and application-owned recovery admission. Provisioning limits the final `otpauth` URI to 512 ASCII bytes and rejects unsafe display labels. See the [TOTP and recovery guide](docs/totp-recovery.md).
- Shared-clock stores for TOTP, WebAuthn and the OAuth issuer: stores return admitted-time observations and contextual commit receipts, and timed operations check immutable minima, authenticated entity floors and temporal predicates against fresh store time. Worker clocks are health inputs, not a time source. Results distinguish definitely unperformed work, uncertain mutation and known commitment that needs reconciliation. WebAuthn and TOTP operation timeouts are at least one second, and each commit's deadline reserves the store's declared UTC error. `WebAuthnStore` implementations must reclaim expired ceremonies, either within successful mutating commits as `InMemoryWebAuthnStore` does or through explicit admitted maintenance; the PostgreSQL example adds a bounded `reclaimExpiredCeremonies` call. The volatile in-memory stores detect host-clock discontinuities and start a new clock generation that fences in-flight work; they resume at once after a forward step and wait for the last published instant after a backward step, keeping stored credentials and factors. TOTP records use the TTR3 format and WebAuthn records the WAR2 format; any other format fails closed. See the [shared-clock store and consumer contract](docs/shared-clock-stores.md).
- A protocol-neutral `BrowserRequestOriginPolicy` with closed, redacted results combines raw `Sec-Fetch-Site` and `Origin` occurrences for browser request admission. The Soklet, Jakarta Servlet and javax Servlet adapters provide extraction helpers. Applications keep host, session, CSRF/action-token and route authorization responsibilities. See the [browser request-origin policy](docs/browser-request-origin-policy.md).
- Bounded Argon2id password hashing, native verifier checks, optional pepper policy and explicit bcrypt/PBKDF2 legacy verification. Applications select shared local work admission and keep account, password and session policy. See the [password hashing guide](docs/password-hashing.md).
- SAML service provider (SP) support, including HTTP-POST Single Logout in both directions with exact-root XML signatures, strict logout semantics and a shared atomic replay domain across POST and Redirect, explicit POST endpoints and metadata, logout form parsing, and Soklet and Servlet transport helpers. See the [SAML SP guide](docs/saml-sp.md).
- SCIM registered schemas and immutable resources, create/PUT validation, schema-bound filter policies, GET/SearchRequest queries, projection, index/cursor page framing, conditional headers, discovery and bounded response preparation. Ordered atomic PATCH and conservative membership reduction include explicit string matching, attempted/effective/supplied paths and PATCH response policy. `ScimResourceType.userInstance()` registers only the core User schema; register `ScimSchema.enterpriseUserInstance()` through `schemaExtensions(...)` to support Enterprise User attributes. The optional `ScimFilterEvaluator` evaluates a policy-approved filter against one resource; applications own collection retrieval, authorization and persistence. See [SCIM server primitives](docs/scim-server-primitives.md).
- Bounded SCIM filter and attribute-path syntax parsing with sealed results and fixed errors, an immutable six-kind AST, a Java 17 visitor, explicit serialization and default-deny policy configuration. Syntax success grants no query permission; the provider binds schemas and enforces complete policies. See [SCIM filter syntax](docs/scim-filters.md).
- Unpublished runnable examples: a self-issued Soklet MCP issuer with app-owned login and consent, a playground with OIDC, SAML and SCIM routes, and OIDC, logout, passkey, TOTP, password, key-import, provider-token and PostgreSQL store examples. They keep their documented state, session and recovery limitations; see [runnable examples](examples/README.md).

### Changed
- The application-side PostgreSQL examples and their current-source qualification fixtures use the released `com.pyranid:pyranid:4.9.0` artifact from Maven Central. Revetsec core continues to have no Pyranid runtime dependency; preserved pre-release evidence retains its historical dependency bytes only within that evidence boundary.

### Security
Pre-release hardening from the October and November 2026 security reviews:
- Shared caches isolate caller cancellation, introspection handles errors per token, injected HTTP authenticators and cookie handlers are rejected, and client-metadata admission, TLS chain construction, HTTP status classification and cache recovery are bounded.
- Refresh ID tokens must satisfy the original flow's ACR acceptance policy, not a different client default (review `3.jose-oauth-and-oidc.6`).
- WebAuthn ceremony expiry, atomic consumption and proof release use admitted store time and final recovery/time admission. Ordinary reads, barriers and no-effect refusals do not reclaim ceremonies or advance floors. Late known ceremony commits require reconciliation, and unknown writes release no proof. Checked reauthentication snapshots the caller's expected account handle before calling the store, so a store callback cannot change the post-commit account comparison.
- SAML text attributes remain visible under mutable unsigned namespace declarations, and any `xsi:type` on XSD-typed text elements is rejected. Replay admission is partitioned by connection. Logout consumes pending state only through conditional atomic `consumeIfMatches` after document validation and authenticated binding/correlation checks, so a signed but semantically invalid logout response consumes nothing; custom pending stores without it fail closed. Logout replay retention covers every supported age/skew policy for POST and Redirect, so a policy change cannot re-admit an accepted message.
- SCIM trusted resource construction and delegated string matching obey configured work limits, and SCIM refuses any submitted value for an assigned immutable attribute that is never returned instead of comparing it with the stored value.
- The Servlet and Soklet adapters validate credential-bearing redirects before writing responses.
- `OutboundUriPolicy.defaultInstance()` rejects the cloud metadata endpoints known as of 2026-09-27 (100.100.100.200, 168.63.129.16, fd00:ec2::23 and fd20:ce::254, and the names `metadata.google.internal` and `metadata.goog` and every name under them), the RFC 8215 local-use NAT64 prefix 64:ff9b:1::/48, and IPv4-translated literals around a rejected IPv4 address.
