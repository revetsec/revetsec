# Ordinary PostgreSQL issuer retention cleanup

The unpublished `PostgresqlIssuerStore.reclaimExpired(maximumRows, remainingBudget)` is an explicit application maintenance operation. Schedule it from trusted application infrastructure; it is never called by ordinary reads or commits and starts no owned thread. Each call admits1–16 rows under one original budget capped at30seconds. Nonpositive budgets and pre-entry cancellation perform no lookup. Permanent issuer and subject kinds are never eligible. Credential expiry, consumption, revocation and capacity pressure do not authorize earlier deletion.

This operation trusts the integrity and ACL protection of **engine-written SQL full-retention metadata**. Carrier reconstruction checks bounded syntax; it does not authenticate an expired encrypted record. Tampered metadata and authentic database rollback require closed recovery/admission procedures. This operation does not inherit MIG12 authenticated-inventory or migration authorization evidence. Current issuer carriers require whole-second retention; the adapter preserves and compares complete seconds/nanos, rejects inconsistent selected nonzero-nanos metadata, and never normalizes it.

One transaction takes shared physical admission, an initial matching healthy authority observation and an indexed lexicographic full-retention selection. It takes sorted strongest entity locks, rereads exact kind/key/version/retention/ciphertext facts, locks changed escrow buckets, then obtains another fresh matching authority observation. The final observation must not precede the selection observation, even when every selected retention horizon is far older than both samples. Every deletion must still satisfy its inclusive full-retention horizon after all waits. Exact conditional deletes and entry refunds commit together. Inconsistent selected metadata/accounting refuses the entire batch; it never skips, guesses, repairs, evicts or retries automatically. A changed admission, generation, error profile or unavailable/late authority closes the operation.

`CleanupResult` carries a fixed status. Only COMMITTED carries a known removed count, including zero for an empty admitted batch. A late known commit preserves that count while `isAcknowledgedWithinBudget()` is false. That timing flag is not current health, deployment readiness or ordinary protocol-success proof. UNKNOWN carries no count or replay permission; reconcile actual effects under the application's protected maintenance policy before another attempt. Fixed redacted result formatting releases no addresses, versions or ciphertext.

Run `python3 examples/postgresql-pending-store/run_issuer_cleanup.py --help` for required selected JDK, six exact JAR paths/digests and a new absolute output directory. The harness uses the existing checksum-selected PostgreSQL image with `--pull=never`; it downloads nothing and removes its own named container, volume, keys and credentials. The runtime role cannot truncate, delete the root registry, relabel kinds or reallocate capacity. Test-only administrative controls seed explicitly opaque mechanics fixtures and inject races/corruption; those credentials are not given to the application adapter. Raw secrets never enter receipts. A preserved old store can run with `--baseline-only --baseline-store ... --baseline-store-sha256 ...`; that lane requires the exact named actual capacity assertion, not a missing method, compilation failure, setup problem or timeout. `--genuine-offset-nanos 1` separately checks genuinely matured rows at E+1ns.

The genuine lane creates all seven kinds through the actual public authorization/code/PKCE/token path, without logging credentials or passing tokens on the process command line. It captures an actual engine transaction that shares an expired assigned bucket, proves capacity refusal before explicit cleanup, proves E−1ns survival and E/e+1ns physical reclamation, then commits that same prepared transaction after the exact refund while permanent fences stay byte-identical.
