# Password and TOTP focused review — 2026-10-16

**Status:** internal, source-bound pre-release qualification of the current uncommitted password-hashing and TOTP/recovery implementation, including one unpublished PostgreSQL TOTP fixture and paired Servlet TOTP cookbooks. This is not an independent cryptographic audit, qualification of arbitrary production stores or cross-host recovery, an API freeze, or a 1.0.0 release sign-off.

## Scope and outcome

The review inspected the selected `com.revetsec.password` and `com.revetsec.totp` core contracts, their tests, implementation guides, runnable examples and the current application-security scope plan. It looked for incorrect proof release, unbounded hostile work, pepper/key rotation gaps, replay or recovery-code reuse, and uncertainty or stale-epoch handling. No confirmed correctness defect remains from this focused pass.

The password checks now include overlapping-thread work-gate accounting, release of a permit after an in-flight Argon2id interruption, a coherent pepper snapshot across rotation and temporary outage, interruption during PBKDF2 work, malformed stored forms under a busy gate and a failing pepper source, and a known-answer Argon2id vector with the public API's actual 32-byte secret length. The last vector was generated from the pinned C reference; the existing tests also compare the translation with RFC 9106, a nine-case pinned C corpus reproduced in a network-disabled Linux container, and Bouncy Castle. These are implementation comparisons, not an external review of the translation. The [source and safety-deviation record](../password-vendored-source.md) names the pinned files and Java-specific changes. A [review packet](password-primitive-external-review-packet.md) identifies the source map, evidence, deviations and questions for an external reviewer.

The TOTP review checked the durable-record and recovery-gate contracts against the in-memory store conformance and authenticator fault tests. It corrected a documentation mismatch: malformed submitted codes up to 128 characters spend an attempt, while longer inputs are rejected before gate or store access. Regressions cover oversized confirmation, TOTP and recovery inputs. Two seeded [fuzz targets](../../fuzz/README.md) alter newly issued TOTP and recovery codes, then require that the unchanged control still succeeds once and replay fails. The [TOTP guide](../totp-recovery.md) states the boundary and the application-owned transaction and recovery obligations.

The [unpublished PostgreSQL TOTP fixture](../../examples/postgresql-pending-store/README.md#durable-totp-fixture) now exercises those contracts on one authoritative primary. Its app-owned store keeps sealed records and epoch history permanent, compares complete snapshots under a namespace-row lock, and fences stale writers in the same transaction. An external one-host marker and gate close admission and drain live permits before an authentic logical restore; the controller then provisions a fresh epoch before ordinary traffic reopens. A separate non-superuser runtime role has no `DELETE` or `TRUNCATE` privilege on the TOTP or test application tables. The fixture's public-API probes cover enrollment, TOTP/recovery races, replay, lost COMMIT acknowledgements, outage/restart, key-material mismatch, key promotion/resealing/retirement, and rejection of old credentials after recovery.

The expanded fixture includes a separate **test-only application-state store** for primary-authenticated pending logins, cookie/CSRF rotation, restricted recovery-code sessions and synthetic session-linked approval markers. It checks pending-login binding, primary session and CSRF before consuming a code, then compares the proof's account, binding and factor ID with the pending record and rechecks active epoch and session state in the application completion transaction under the same external permit. Per-epoch application clock state rejects backward time that could revive expired rows. The application probes cover pre-admission rejection without spending a valid code, failed proof without completing a login, uncertain application COMMIT without credential release, two JVMs consuming two distinct valid recovery codes with one session winner, and a controller close between proof and completion that withholds the session. Another pause advances application time past the pending-login deadline after proof and rejects completion; a fresh-epoch factor replacement rejects a replacement-factor proof against a pending login pinned to the removed factor. The authentic logical restore includes application rows; closed admission prevents their use, and fresh-epoch checks reject the old session, pending login and approval marker after reopening. The test's synthetic primary authentication and approval marker are not production session or action-bound one-use approval implementations. The paused proofs test the gap before application SQL begins; they do not prove a controller drains an already in-flight application transaction.

The paired [Jakarta Servlet](https://github.com/revetsec/revetsec-servlet-jakarta/blob/main/docs/totp.md) and [Javax Servlet](https://github.com/revetsec/revetsec-servlet-javax/blob/main/docs/totp.md) cookbooks call core directly from application-owned routes, without adding a Servlet TOTP helper. Their Java 17 sources and real-container fixtures cover enrollment and confirmation, TOTP and recovery login, authorized GET/HEAD status, recovery-code rotation and factor removal. The local HTTP checks include hostile Origin, CSRF, duplicate cookie and media headers, body limits, code replay, session/CSRF rotation, closed admission, late permit close and a lost final commit acknowledgement that withholds a cookie. The fixtures use synthetic primary authentication, volatile state and a one-JVM test gate; their pending logins omit fixed expiry and factor-generation pinning. Those predicates are exercised in the separate PostgreSQL fixture, not in either Servlet container. The Servlet runs do not establish production session policy, durable storage, an in-flight application transaction drain or cross-host recovery.

The [threat model](../threat-model.md) and [security invariants](../../SECURITY.md) now map `INV-SEC1` and `INV-SEC5` to executable checks. The [candidate core API inventory](rc-sec-core-api-candidate-2026-10-16.md) lists the password and TOTP declarations, result paths and bounded contracts. The exported API audit now includes both packages, with a sentinel against accidental omission. The [compatibility ledger](../../COMPATIBILITY.md) names the new packages. The private application-security scope plan identifies password hashing and TOTP/recovery as selected while leaving password policy, breach checking and ten other candidate rows provisional. The standalone [password example](../../examples/password-hashing/README.md) is compiled as Java 17 source and run in the supported-JDK CI matrix. The site guides explain the same code-length and bcrypt-interruption boundaries.

## Evidence and limits

- The local focused password tests, TOTP boundary regression, threat-model map and password example compile/run passed on Java 17. The Soklet 4 TOTP example passed its warning-fatal compile, explicit-nullability audit, boundary/lifecycle checks and loopback socket checks on Java 21 and 27 against the checksum-pinned framework JAR. The website build, documentation/source-link checks, metadata, presentation, search and lint checks passed. The full core Java 17 suite, Java 21 static-analysis profile and warning-fatal Javadoc gate are recorded below.
- The pinned Spring bcrypt implementation checks interruption before and after its calculation, not inside it. A canceled in-flight bcrypt call can retain its caller thread and local work-gate permit until the bounded calculation finishes. Benchmark the highest enabled migration cost and concurrent call limit on target hardware; remove the legacy path when migration ends.
- `TotpStoreConformanceTests` still has only an `InMemoryTotpStore` subclass; the PostgreSQL fixture tests the same observable conditions through separate Java 17 probes and adds real multi-process, primary-restart, lost-acknowledgement, key-retirement and authentic-restore evidence. Its local file marker and OS lock qualify one host and one primary only. It exercises test-only application session transactions but does not qualify a production session store, purpose-bound management approvals, a production connection pool, cross-host admission or failover, physical power-loss durability, or arbitrary `TotpStore` implementations. Every fixture read and commit serializes on a namespace row. The held-row test proves bounded fail-closed behavior; the workload lane measures this fixture's namespace-lock path without setting a performance threshold. A static marker cannot detect an unannounced backup rollback within the currently active epoch.
- The paired Servlet cookbooks and Tomcat fixtures narrow application HTTP coverage but do not close the formal M12 S1–S4 manual pentest or the RC-SEC production application-session design. Both hosted adapter CI core pins predate TOTP; local source-bound receipts are not hosted CI qualification on pushed source.
- The [password workload probe](../../verification/password/README.md) and [local raw measurements](../../verification/password/evidence/2026-10-16/README.md) exercise actual Argon2id, bcrypt and process-local gate paths. The PostgreSQL fixture records four-JVM lock latency and throughput in its receipt. Both are synthetic observations, not production sizing; they need repetition with the intended CPU, memory, JVM, connection pool, record population and traffic mix. External review of the internal Argon2id/BLAKE2b translation remains a separate release gate. The owner must complete the selected core API freeze, production application session/epoch-fence design and qualification, applicable adapter/cookbook qualification, and hosted CI on pushed source before 1.0.0.
