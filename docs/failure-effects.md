# Temporary conditions, effects and replay

`RevetsecException.isTemporaryCondition()` reports a fixed failure classification. It does not establish that a request was unsent, had no effects, remains usable or is idempotent. A false value does not prove a permanent condition or zero effects. HTTP 429/5xx, `temporarily_unavailable` and a timeout can follow remote consumption or commitment.

The public getter replaces `isTransient()` before 1.0.0, without an alias. Its boxed Boolean type and classifications are unchanged. The SAML NameID format method with that spelling is unrelated and remains. No universal `isRetryable()` or automatic retry layer is provided.

## Handle each operation's outcome

| Operation | Effect boundary and permitted handling |
| --- | --- |
| Metadata / discovery / JWKS GET | Read-only protocol retrieval; cache/health/cooldown mutations are local. A surrounding callback may already own/consume state. A separately admitted bounded retrieval can repeat under its cache/egress policy. Do not replay surrounding code/refresh/callback because retrieval is repeatable. |
| UserInfo / introspection retrieval | Read-only resource/identity retrieval with credential-specific validation; shared health recovery is separate from caller result. No same-call retry. Later independent bounded retrieval does not repeat authentication, session creation or token issuance. |
| Client-credentials acquisition / source renewal | Remote POST can issue credentials before acknowledgement. Failure or invalid/late response does not establish no issuance. Existing cached credential may remain valid under cache policy. One acquisition POST per leader attempt. A later explicitly authorized fresh acquisition may be permitted by app policy; it is not exactly-once replay. Never replay the protected resource/business action on this flag. |
| OAuth authorization-code redemption | Remote code may be consumed before a transport/parse/late failure. A true `isTemporaryCondition()` value does not mean unsent or no-effect. No automatic second token POST. Pending-store mode consumes local record once; a new auth flow must be explicitly authorized, not regenerate/redeem silently. |
| OAuth / OIDC rotating refresh | Remote refresh may rotate/consume old credential; a returned ID token can then fail local continuity/ACR/type checks, withholding all returned secrets. Do not resend old refresh on temporary flag, 429/5xx, timeout or malformed response. Keep omission-of-replacement behavior only on successful checked response; uncertain rotation requires provider/app recovery. |
| OAuth / OIDC browser callback | Atomic store consume precedes release/exchange checks; it can remove pending state even if later work fails. Sealed-cookie-only mode has no server atomic consume. No generic callback replay or read rescue. Only genuine success can create/rotate application session; rejected/unknown callback is not an instruction to generate a new flow automatically. |
| OAuth / OIDC logout pending save and return | SAVED permits delivery only after core wrapper budget checks; entered throw/null/late maps INDETERMINATE. Logout entered consume throw/null/late is STORE_INDETERMINATE, no output. Local session close may already be known or possible. No retry/save regeneration/read rescue. Callback result is correlation only; never reattach local session or clear newer independent session. |
| SAML auth/logout browser callbacks / pending saves | Forged/invalid response can leave valid pending state available; validated terminal response consumes matching pending/replay atomically. Uncertain consume/save releases no success. Do not automatically repeat callback, create session, replace pending RelayState or treat no response as rollback. Preserve existing invalid-response-versus-terminal-consume distinction. |
| Selected issuer TIMED mutations / service output | UNKNOWN means uncertain authoritative commit. COMMIT_CONFIRMED_NOT_ADMITTED is known committed but ordinary output withheld; both nontransient trusted store reasons. Raw initialization/reseal return factual receipts even late. Only known-zero-effect CONFLICT may trigger existing bounded fresh-fact internal retry under original deadline. UNKNOWN/known-withheld never replay mutation automatically; no matching-looking read as ack. Remote fixed503/no credentials/redirect/Retry-After. |
| Selected WebAuthn ceremony / management mutations | Succeeded proof only after admitted commit/final recovery. Indeterminate uncertain target write; ReconciliationRequired known target commit with withheld ordinary output. Rejected account/purpose check can follow consumption because checked wrapper runs after generic completion. No proof/session/action on non-success. Do not resubmit same ceremony or repair established account roots; explicit current authorized management/status paths remain separate. |
| TOTP verification / recovery / enrollment / rotation | Unavailable/Rejected do not imply zero total operation effects: prior confirmed charge/fence/floor can survive. Indeterminate uncertain target; ReconciliationRequired known target committed/output withheld, no proof/codes. No charge refund, second target callback, recovered secret batch or same-operation retry. Later explicitly authorized management operation is new work, not rescue of withheld output. |
| Ordinary issuer physical retention cleanup | COMMITTED count factual even late (timingflagfalse); UNKNOWN no guessed count. Physical GC is neither protocol success nor readiness. No automatic retry/read rescue; only separately authorized maintenance under trusted SQL metadata and healthy nondecreasing authority. No MIG12 proof transfer. |

Pure retrieval may have cache/health effects, and an otherwise read-only retrieval can run after a callback has already consumed pending state. Repeatability of a GET does not propagate to the surrounding authentication, refresh, session or business action. Client-credentials acquisition can be newly authorized under application policy; an ambiguous previous issuance is still not exactly-once success.

`UNKNOWN`/`Indeterminate` means uncertain effects. A later matching-looking read is not a commit acknowledgement. `ReconciliationRequired` and issuer `COMMIT_CONFIRMED_NOT_ADMITTED` mean known commitment with ordinary output withheld. Do not collapse those outcomes into unknown commitment, invalid credentials or ordinary success. The issuer's fixed commit outcomes remain nontemporary, without implying permanent failure or zero effects. Existing bounded retry of a known-zero-effect conflict keeps its original fresh-fact/deadline contract.

Earlier confirmed charges or fences can precede a later rejected/unavailable TOTP target; they must not be refunded or ignored. A charged operation can have one earlier confirmed callback and one unknown target callback without retrying the target. A checked WebAuthn reauthentication context mismatch can follow ceremony consumption: rejection is not a general assertion of zero effects. Explicit status/reconciliation and newly authorized management operations retain their separate contracts.

## Keep application effects separate

A library proof/result does not atomically create an application session or authorize a sensitive action. Applications check their own current session/account/CSRF and consume their own one-use action. An application commit can be known or uncertain separately from the library transition. Generic private/no-store remote errors may hide diagnostics while trusted local logic retains the effect distinction.

A pending save that was entered and then returned late/null or threw is indeterminate, including when it physically saved. Do not regenerate/deliver a prepared credential or retry the save because the condition might be temporary. Atomic-store callback consumption and cookie-only correlation have different concurrent single-use properties; cookie clearing does not make concurrent code POSTs impossible.

For [RP-Initiated Logout](oidc-logout.md), authorize the local POST/CSRF and close the session before provider preparation. A failed/uncertain provider or output step never reattaches that session. Callback correlation never authenticates a user or deletes a newer independent session. Token revocation remains an explicit separate operation.

A diagnostic `Retry-After` value is no permission to replay an unsafe operation. Selected issuer uncertainty/known-withheld responses remain fixed private503 `server_error` without credentials, redirect or Retry-After; selected factor recipes use hints only on their explicit throttled branch. Transport/profile observations, application state, physical devices, durable recovery and release acceptance retain their own qualification requirements.
