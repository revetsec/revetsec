# Threat Model

**Status: foundations only.** Revetsec holds its shared foundations (milestone M1) and no protocol code yet. This page grows as each protocol area lands, and it is complete before 1.0.0.

## Actors

The design considers these attackers:

- a malicious browser user attempting login CSRF, code or response injection, mix-up, or open redirects;
- a malicious tenant identity provider or OpenID Provider: in a multi-tenant application, one customer's IdP is hostile to every other customer and can assert any email, NameID or attribute;
- a network attacker (TLS is assumed, and Revetsec never downgrades it);
- an authenticated but hostile SCIM client;
- an attacker sending oversized, deeply nested or otherwise pathological input to exhaust resources;
- server-side request forgery through tenant-supplied issuer or metadata URLs;
- an operator who has changed JVM-wide security settings.

## Assets

Account identity (who is logged in, and as which tenant), session establishment, tokens and authorization codes, service-provider private keys and sealing keys, and provisioning integrity (which users exist and which groups they belong to).

## Trust boundaries

Browser to application; application to authorization server, OpenID Provider or identity provider (outbound HTTPS); identity provider to application (front-channel POST); SCIM client to application.

## Invariants and tests

Each security invariant is listed here with its stable ID, its scope so far, and the tests or build checks that enforce it. Every listed invariant must map to at least one of them, and CI will check the map. Protocol invariants are added as the code that upholds them lands. The "Security Invariants" section of [SECURITY.md](../SECURITY.md) carries the same list.

Test classes are named relative to [`src/test/java/com/revetsec/`](../src/test/java/com/revetsec/), and the fuzz targets relative to [`fuzz/src/test/java/com/revetsec/`](../fuzz/src/test/java/com/revetsec/). CI's `test` job runs the tests on JDK 17, 21, 25 and 27, its `fuzz-regression` job replays every fuzz target's seeds, and ClusterFuzzLite fuzzes the targets on pull requests, and nightly once its corpus storage is set up.

## Outbound HTTP

Revetsec's protocol types will send every request through one internal helper on the JDK `HttpClient`. The helper exists now, and no public type uses it yet. This is what it does and does not protect.

**The outbound URI policy looks only at literals.** `OutboundUriPolicy` classifies IP address literals by their text: dotted-quad, all-digit (`https://2852039166/` is 169.254.169.254), bracketed IPv6, and the IPv4 addresses inside IPv4-mapped, IPv4-compatible and NAT64 IPv6 addresses. Its classifier also reads the short forms the JDK accepts (`127.1`, `169.254.43518`), but `java.net.URI` finds no host in a URI such as `https://127.1/`, and the policy rejects every URI without a host. `OutboundUriPolicy.defaultInstance()` rejects link-local literals (169.254.0.0/16, which holds the common cloud metadata address 169.254.169.254, and fe80::/10), the IPv6 metadata address fd00:ec2::254, and any-local literals (0.0.0.0/8, so `https://0/`, and `::`), as well as IPv6 literals with a zone ID and schemes other than `https` and `http`. It permits loopback and private literals, and a stricter policy is still to be decided before 1.0.0. Checked by `OutboundUriPolicyTests`, which compares every literal row with `InetAddress.getByName`, rejects `https://127.1/` and `https://169.254.43518/`, and asserts that the policy's classes do not even reference `InetAddress`.

**Hostnames are never resolved.** So no policy stops a DNS name that resolves to a private or metadata address, or a name whose answer changes between checks (DNS rebinding).

**Numeric-looking hosts that are not strict literals are rejected, because of the JDK itself.** The JDK's own literal parser does not parse hex forms, or numeric forms longer than 15 characters, such as `0xa9fea9fe` and `0251.254.169.254`. It hands them to the platform resolver, and some resolvers read them as addresses: the macOS resolver reads `0xa9fea9fe` as 169.254.169.254. A URI with such a host could therefore reach the metadata address through the JDK alone, with no proxy involved. So the policy rejects every host whose last label is all digits or a `0x` hexadecimal number but that is not a strict literal, and every IPv4 literal with a leading zero in a part, which the JDK reads as decimal and other software as octal. Checked by `OutboundUriPolicyTests.hostsThatLookNumericButAreNotStrictLiteralsAreRejected`.

**Use an egress proxy for URLs that tenants supply.** When issuer, metadata or key-set URLs come from someone you do not control, give Revetsec an `HttpClient` whose proxy enforces the destinations you allow, and keep `https`. That proxy, not the URI policy, is what stops a DNS name that points inside your network.

**Redirects are never followed.** Every 3xx response is rejected, and Revetsec refuses an injected `HttpClient` that follows redirects: a client that did could re-send a POST, `client_secret` included, to wherever a 307 or 308 points. Checked by `internal.http.HttpExchangeHostileTests.aClientThatFollowsRedirectsWouldHaveRequestedTheRedirectTarget` (the redirect target's hit count stays zero) and `internal.http.HttpExchangeTests.refusesAnInjectedClientThatFollowsRedirects`.

**Responses are bounded before they are read.** Besides the size limits under INV-G2, a 2xx with a `Content-Encoding` other than `identity`, a framing anomaly (duplicate or malformed `Content-Length`, `Content-Length` with `Transfer-Encoding`, a `Transfer-Encoding` other than `chunked`) or an unexpected media type is rejected. Revetsec makes these checks when the JDK hands it the response, before any of the body is read, and each of these rejections makes the JDK close the connection. Checked by `internal.http.HttpExchangeHostileTests`, which runs each of these cases against a raw TLS server that observes the close. Three cases fall outside this, and are described below: a response head the JDK refuses to parse, and a 204 (No Content) with a `Content-Length` other than `0` or with a `Transfer-Encoding`, both of which the JDK fails itself before Revetsec sees the response; and an injected client that does not pass cancellation through.

**The per-request timeout bounds the body.** Revetsec waits for the whole exchange, body included, for at most the smaller of the per-request timeout and the time left on the call's total deadline, on every JDK. Only from JDK 26 does `HttpRequest.timeout` cover the body by itself. Checked by `internal.http.HttpExchangeDeadlineTests.theRequestTimeoutBoundsATrickledBodyOnEveryJdk`.

**Keep blocking work off the common pool, or size it** (the system property `java.util.concurrent.ForkJoinPool.common.parallelism`). The JDK completes the `sendAsync` future, and reports failures that happen before a response arrives (a refused connection, a TLS failure, a header timeout), on the `ForkJoinPool` common pool. Revetsec never waits on that future: it waits on an outcome its own body subscriber completes, so a busy common pool does not delay an exchange that gets a response. But while every common-pool thread is blocked, a failure before the response reaches Revetsec only at the call's total deadline, as a timeout rather than an I/O failure, so an unreachable endpoint holds each caller for the full deadline (15 s by default). It still fails closed. Checked by `internal.http.HttpExchangeDeadlineTests.aSaturatedCommonPoolNeitherDelaysAFinishedExchangeNorHoldsARefusedOnePastTheDeadline`. Whether an injected client with its own executor avoids this has not been checked.

**The default client.** When an application injects no `HttpClient`, Revetsec creates one per JVM, on first network use and never while building: HTTP/1.1, no redirects, a 10-second connect timeout, no cookie handler or authenticator, and the default proxy selector and `SSLContext`. It starts the JDK's own threads; Revetsec's own code starts none. Checked by `internal.http.ZeroThreadBuildTests.buildsStartNoThreadAndLoadNoClientAndFirstUsesShareOneDefaultClient` and `internal.http.DefaultHttpClientHolderTests.theDefaultClientHasTheD36Settings`.

**A failed default client stays failed.** If the default client cannot be created, for example because `javax.net.ssl.keyStore` names a missing file, every call fails as a configuration error (the internal kind `DEFAULT_CLIENT_UNAVAILABLE`) until the JVM restarts, and no `Error` escapes (`internal.http.DefaultHttpClientHolderTests.aHolderStartupFailureGivesDefaultClientUnavailableOnEveryCallAndNoErrorEscapes`, in a child JVM). A `VirtualMachineError` during that first creation, such as an `OutOfMemoryError`, or a `StackOverflowError` when the first use comes from a very deep stack, reaches that one caller, and the default client then stays unavailable for the life of the JVM. That is inherent in the class-initialization holder that creates the client lazily. An application that cannot accept it injects its own client.

**The response head is the JDK's, and a refused head leaves the connection open.** Revetsec does not count response header bytes itself. The JDK `HttpClient` refuses a header section larger than the JVM-wide system property `jdk.http.maxHeaderSize` (384 KiB by default), which Revetsec cannot set, because it applies to the whole JVM. It also refuses a malformed head, such as an invalid status line (`HTTP/1.1 099`) or a header name with a space in it. Each refusal reaches Revetsec as an I/O failure, which counts as transient, and the JDK then leaves the connection open until the server closes it (seen on JDK 17.0.20, 21.0.11, 25.0.4, 26.0.1 and 27). Revetsec has no handle on that connection to close it. So a hostile server can keep one connection open for each call, with a response head of a few bytes, and one more for each retry. The mitigation for URLs that tenants supply is an injected client behind an egress proxy that closes idle connections. Which older JDK 17 updates lack `jdk.http.maxHeaderSize` has not been checked. Checked by `internal.http.HttpExchangeHostileTests`, whose catalog includes a 512 KiB header section, an invalid status line and an invalid header name: each gives an I/O failure, and the open connection is not asserted.

**A 204's framing is the JDK's.** For a 204 (No Content), the JDK checks `Content-Length` and `Transfer-Encoding` itself, before it hands the response to Revetsec. A 204 with a `Content-Length` other than `0`, or with any `Transfer-Encoding`, therefore fails as an I/O failure, which counts as transient, and not as a framing rejection. That includes the framing anomalies above, such as two `Content-Length: 7` fields, or `Content-Length` with `Transfer-Encoding`. Where the JDK can parse the `Content-Length` (such as `7` or `-1`), or the anomaly is a `Transfer-Encoding`, it closes the connection. Where it cannot (such as `0x7`, `7, 7` or twenty digits), JDK 17 to 26 leave the connection open until the server closes it (seen on 17.0.20, 21.0.11, 25.0.4 and 26.0.1), and Revetsec has no handle on that connection to close it; JDK 27 closes it. As for a refused head, a hostile server can then keep one connection open for each call and each retry, and the mitigation is JDK 27, or an egress proxy that closes idle connections. A 204 whose `Content-Length` fields are all `0` reaches Revetsec's checks as usual, so two of them are a framing rejection. Checked by the 204 cases in `internal.http.HttpExchangeHostileTests`, which assert the outcome on every JDK, and the client's close wherever the JDK closes the connection.

**An injected client must pass cancellation through.** For a `Content-Length` the JDK cannot parse, such as `7, 7`, `0x7` or twenty digits, the JDK fails the exchange after Revetsec's checks have run but before it subscribes Revetsec's body subscriber, which otherwise cancels the read. Revetsec's rejection, or its dropped error body, then closes the connection only by cancelling the future that `sendAsync` returned. An injected client that wraps the JDK's client and returns a future of its own, one whose `cancel` does not reach the JDK's future, gets the same outcome (a framing rejection, a body too large, or an error status with its body dropped), but the connection stays open: on JDK 17 to 25 until the server closes it, and on JDK 26 until the request's timeout, the smaller of the per-request timeout and the time left on the deadline (seen on 17.0.20, 21.0.11, 25.0.4 and 26.0.1). JDK 27 closes it. Every other rejection closes the connection behind such a client too, because Revetsec cancels the body subscription itself. A client that decorates the JDK's client should return the JDK's future, or cancel it when its own future is cancelled. Checked by `internal.http.HttpExchangeHostileTests.aDecoratingClientKeepsEveryOutcomeForAContentLengthTheJdkCannotParse`, which asserts the outcome on every JDK and the close from JDK 27.

**HTTP/2 on an injected client is untested.** The default client is pinned to HTTP/1.1, and every HTTP test runs over HTTP/1.1, because the JDK's test server speaks nothing else. An injected client may negotiate HTTP/2. On HTTP/2, the size bounds rely on the same subscriber, with the JDK's per-stream flow-control window of 16 MiB, which was read from the JDK source and not observed at run time. And Revetsec cancels the exchange from inside `BodyHandler.apply` on every early rejection; that this closes only the one stream and never hangs has been checked on HTTP/1.1 only. Until HTTP/2 is tested, an application that injects a client and relies on these bounds can pin it to `HttpClient.Version.HTTP_1_1`.

## Known gaps

- **Recursion.** The JSON parser recurses, with depth capped at 64. That depth is tested in a child JVM with a 256 KiB thread stack and the interpreter only (`-Xss256k -Xint`); parsing on a virtual thread is untested.
- **Hashing JSON values.** No JSON value type is `Comparable`, and every type's hash is easy to collide. A `JsonString` hashes as its `String` does, objects and arrays combine the hashes of their contents, every number beyond the range of `double` hashes as positive or negative infinity, and every nonzero number too small for a `double` as positive or negative zero. A `HashMap` or `HashSet` cannot order keys whose hashes collide unless they are `Comparable`, so one keyed by JSON values an attacker chooses does quadratic work: adding 32,768 strings that share one hash to a `HashSet` took about 3.4 s as `JsonString`s and about 8.5 s as single-member objects holding them, against 5 ms as plain `String`s (JDK 17 and 21). Nothing in Revetsec hashes JSON values yet. Do not key a hash-based collection by untrusted JSON values. SCIM's PATCH value matching, which compares values an attacker chooses, is to be designed around this before SCIM lands.
- **Values that share children.** The JSON model's depth cap bounds recursion, not work. A value that an application builds can hold the same child in several places, and `toJson()` and `equals` visit that child once for each place it appears. So a value of a few dozen objects that nests one child twice at every level can make `toJson()` run out of memory, and `equals` against a copy built separately take exponential time. Values the parser returns never share children, so their cost follows the size of the input.
- **Colliding member names.** The JSON parser detects duplicate member names with a `HashMap`, so names chosen to collide cost O(n log n) rather than O(n): about 130 ms for 99,000 colliding names in one object.
- **Connections a hostile server can hold open.** A response head the JDK refuses (on every JDK tested) and a 204 whose `Content-Length` the JDK cannot parse (JDK 17 to 26) each leave the connection open for as long as the server keeps it, and Revetsec cannot close it; see "Outbound HTTP". Both reach Revetsec as transient I/O failures, so each call to such a server, and each retry, can hold one more connection. A `Content-Length` the JDK cannot parse does the same behind an injected client that does not pass cancellation through (JDK 17 to 25, and on JDK 26 until the request times out). The protocol areas are to bound their retries and repeated fetches with this in mind, and URLs that tenants supply belong behind an egress proxy that closes idle connections.
- **Text in I/O causes.** An I/O failure keeps the JDK's `IOException` as its cause, and that exception's message can contain text the server sent, such as a malformed status line. Revetsec's own messages never contain input.
- **Deserialized exceptions.** A crafted serialized stream can produce a Revetsec exception that breaks its constructor's rules; see "Exceptions and Java Serialization" in [SECURITY.md](../SECURITY.md).
