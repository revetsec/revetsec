# RP-Initiated OIDC Logout

`OidcClient` prepares an explicitly requested browser logout and correlates its return. The application owns the local session, POST/CSRF authorization, credential storage, browser response and any token revocation. A successful return proves correlation only. It does not authenticate a user, create a session or prove that every provider session ended.

Configure one fixed registered `postLogoutRedirectUri` on the client. It must be HTTPS, or use the existing explicit insecure-loopback test option, without query, fragment or user information. The provider's optional `end_session_endpoint` comes from trusted supplied metadata or strict discovery. There is no inferred endpoint or fallback. Its URI must pass the configured outbound policy before a browser request is exposed. Injected HTTP clients must use `Redirect.NEVER` and have no `Authenticator` or `CookieHandler`; applications own TLS, proxy and egress policy.

## Retain the hint explicitly

After genuine authentication, call `client.logoutHintFrom(authentication)` only if the application wants provider logout. Only authentication produced by that exact client instance is accepted. The returned `OidcLogoutHint` contains the original comparison-only session reference and validated compact ID token. It is a credential for trusted storage, not identity proof. The `OidcSessionReference` version-2 storage format retains the original flow's ACR acceptance policy and contains no compact token. Version-1 references lack that policy and are rejected, including when embedded in old retained hints; clear them and authenticate again. See the [flow assurance and reference migration policy](oidc-flow-assurance.md).

The refresh overload accepts only a genuine result from that exact client. It returns an optional replacement hint when the refresh contains a newly validated ID token. Keep the original reference for continuity; replacing a hint must not replace it. Expiry of the original ID token does not by itself prevent its later use as a logout hint.

Explicit `toSerializedForm()` emits a credential-bearing JSON envelope; never log it. Restoration with `fromSerializedFormResult` checks structure and continuity without authenticating a new identity or validating a signature. Protect that storage's confidentiality, integrity and access. Typed `toSealedForm(sealer, context, lifetime)` and `fromSealedFormResult` use a dedicated purpose and the sealer's configured clock. Valid large hints can exceed the unchanged sealer limit: default 3,800 characters, maximum 16,384. Refusal does not permit truncation, chunking or plaintext browser delivery. Immutable strings and provider copies cannot be deterministically wiped.

## Terminate locally, then prepare and save

Authorize the application's local same-origin POST and session-bound CSRF value against current session state. Atomically detach the local session before discovery or provider preparation. An unavailable provider, rejected URI, failed save, interruption or closed browser must never reattach it. Distinguish a denied local request from an uncertain local close, and do not retry a possibly applied close as if it were unperformed.

Call `client.beginLogout(originalReference, retainedHint)` after that transition. It checks binding before discovery, entropy or output and returns an `OidcLogoutRequest` plus independent `PendingOidcLogout`. No end-session server request is sent. The request's redirect/form getters deliberately emit the ID-token credential; ordinary text rendering is redacted. Choose one trusted startup delivery policy. Form POST avoids putting a large hint in a redirect header; HTML output must escape all fields and use no-store/no-referrer and an appropriate content security policy. A bounded core representation is not proof of a browser or provider's maximum URL capacity.

Save or seal the pending record before delivering that request. It contains only correlation state, configured client/issuer, callback and exact times, without token, nonce, PKCE verifier or application identity. On the store path, generate an independent [`BrowserBinding`](https://javadoc.revetsec.com/com/revetsec/BrowserBinding.html), retain it in protected server session state, and call `getPending().saveToResult(store, binding, remainingBudget)`. **Only `SAVED` permits browser delivery.** `INDETERMINATE` includes late, null, throwing or possibly completed store calls; do not retry or expose the prepared credential. Application work and core calls must fit the application's original shrinking budget. The logout operation retains its narrower nonempty, well-formed 512-code-unit and 512-byte rule even though the carrier has a broader restoration ceiling. A callback cookie is only an untrusted lookup/comparison value; recover the retained carrier from server state rather than passing request text to `BrowserBinding.fromTrustedPersistence`.

`PendingAuthorizationStore` remains an opaque trusted plaintext store. Its browser-binding digest is unkeyed and supplies no record authentication. The backend must protect confidentiality and integrity and implement atomic consume across participating nodes/restarts. The existing default 8 KiB store budget may refuse a permitted 16 KiB logout record. Capacity refusal must not evict unrelated live state.

## Correlate the return

Use the actual callback URI from trusted routing configuration. Pass its raw query, the typed browser-specific `PendingOidcLogoutSource` and that fixed URI to `completeLogoutResult`. The raw query must contain exactly one literal `state` parameter and no other parameters. Malformed encoding, aliases, duplicates and protocol-response confusion reject before consume.

A store source consumes exactly once. Expiry equality is expired; rollback before creation rejects. A late, null or throwing consume is `STORE_INDETERMINATE`, not a hostile-user success or permission to retry. The interrupt flag is preserved. No discovery, JWKS, token exchange, signature verification or session creation occurs on return. `Returned` is payload-free correlation; `Rejected` exposes only a fixed reason.

A typed sealed-cookie source is also available. Clear that cookie on every callback, including rejection and exception paths. Cookie clearing cannot supply atomic concurrent single use. Clear only the logout correlation cookie: an older callback must not delete a newer authenticated application session. Use an appropriately qualified atomic shared store when cross-node single use is required.

Token revocation is a separate, explicit application action with its own admission, time budget and outcome handling. This feature adds no front-channel or back-channel logout notifications, OpenID Provider or general session-management service. Local component checks, actual provider/browser interoperability, durable deployment qualification and final release acceptance remain distinct gates.
