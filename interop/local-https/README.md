# Local HTTPS for Revetsec examples

The recipe uses current published official Caddy 2.11.4, pinned by the multi-platform digest in `pins.json`. Latest upstream 2.11.6 was published October 1, but its official Docker tag had not yet been published when selected; that difference is explicit in the pin. The task also checksum-verified the official 2.11.6 mac arm64 binary. No compatibility claim is made from metadata alone.

Run `python3 interop/local-https/prepare.py --work-dir /absolute/new/private-tls-directory --openssl /absolute/path/to/openssl`. The directory must be new. Its CA and leaf key remain private, and every certificate has a two-day lifetime. The leaf includes DNS SAN `localhost` and IP SAN `127.0.0.1`; positive hostname/IP and negative foreign-host verification are mandatory. Keep this directory outside source control.

Set `REVETSEC_TLS_CERT` and `REVETSEC_TLS_KEY` to the generated `localhost.crt` and `localhost.key` paths. Start the frontend HTTP listener at 127.0.0.1:8080 and MCP listener at 127.0.0.1:8081. Start the pinned Caddy image with an already-enabled Docker host network, the exact Caddyfile, and read-only certificate mounts. On Linux this is `docker run --rm --network host --cap-drop ALL --security-opt no-new-privileges ... caddy:2.11.4@sha256:0c994536bddb66445885237f1a5dcc1916bccea922661c76b4e9fc24061f9b52 caddy run --config /private/Caddyfile`. Use a task-private writable Caddy data/config directory; no user/shared directory mounts. Docker Desktop host networking must already be enabled and its127.0.0.1 behavior verified. Otherwise run Caddy, example apps, local provider, Inspector and headless browser inside one disposable container so their listeners remain 127.0.0.1. Do not substitute a wildcard bind or tunnel.

The frontend receives Host `localhost:8443`; protected-resource metadata stays on the frontend route. The MCP backend receives Host `127.0.0.1:8081`. Apps still validate the actual Origin and Host, and CSRF/session checks remain enabled. The trusted MCP resource is `https://localhost:8443/mcp`; the Playground OAuth redirect is `https://localhost:8443/oidc/callback`. Secure/HttpOnly/`__Host-` cookie behavior is retained.

For manual browsing, the owner chooses whether and how to trust this disposable CA. The tooling never adds it to the global or user macOS keychain. For unattended Linux Chromium, create a private HOME and `sql:$HOME/.pki/nssdb`, then import only `ca.crt` with NSS `certutil`; destroy that disposable profile/store after the run. Use a nonroot browser and retain its sandbox. For the Inspector Node backend, set `NODE_EXTRA_CA_CERTS` to the task CA only. For Java, create a new task-only truststore and pass `-Djavax.net.ssl.trustStore=/private/...` explicitly. Never alter the installed JDK's cacerts. No hostname checks or certificate-error bypass flags are permitted.

`curl --cacert /private/ca.crt https://localhost:8443/` and Java/Node default hostname verification should succeed. An unknown certificate, foreign hostname and nonloopback Host/Origin should remain rejected. No local key, token, cookie, browser storage or raw OAuth body belongs in durable evidence.

The local Caddy edge rejects comma-materialized Authorization, Origin, Content-Type and Cookie headers before forwarding, including duplicate physical fields whose values are identical or whose names differ by case. This stricter Content-Type rule is scoped to these examples' accepted single media type/form charset. Ordinary browser HTTP/2 cookie coalescing uses semicolons and remains accepted. Caddy must reject duplicate Host itself. The adapter's identical physical Authorization boundary is still recorded; this edge does not change that API limitation.

The second site is `https://localhost:8445`: barebones HTTP listens at 127.0.0.1:8082; the edge preserves Host `localhost:8445` and applies the same sensitive-header deny rule. Its provider redirect is `https://localhost:8445/callback`.
