# Self-issued browser interoperability fixture (unpublished)

This consumer fixture runs the [self-issued Soklet example](../../examples/self-issued/README.md) with unmodified released MCP Inspector 2.9.0 and Chromium. The application supplies users, registrations, sessions, consent and keys; Revetsec supplies OAuth issuance and checked online resource admission. No third-party security assessment is claimed.

Each invocation uses a fresh issuer namespace and isolated container. No hosted identity provider, DCR, endpoint override, client patch or preloaded OAuth result is used. The ordinary client UI performs login/consent, discovery, code exchange and tool calls; optional recovery modes exercise real expiry/refresh or fresh scope-step-up consent. The second call selects another tenant and observes application denial.

## Prepared inputs

Use linux/arm64. Build the example with its documented `build.py` against exact core/helper sources and the approved Soklet 4.0.0 JAR. Copy the four resulting JARs to a private `app` directory. Supply a JSON array of four `{ "name": "filename.jar", "sha256": "..." }` rows, using the hashes in the build's `RESULT.json`. The filenames are `self-issued-1.0.0-SNAPSHOT.jar`, `revetsec-1.0.0-SNAPSHOT.jar`, `revetsec-soklet-1.0.0-SNAPSHOT.jar`, and `soklet-4.0.0.jar`. Keep build source inventories with the receipts.

Prepare the browser image using the existing [pinned Dockerfile and context preparation](../inspector-auth/linux/README.md). The pinned npm lock/integrity, Playwright image, Chromium and NSS package are reused. Pass an already present immutable image ID via `--image`; the default is the locally qualified image ID. A rebuilt image produces its own evidence identity. Runs never pull images or contact external services.

Prepare a private `runtime` directory containing:

- `java/`: `/opt/java/openjdk/` extracted from `eclipse-temurin@sha256:c2c0deda43a14dea9d5c6c5349d22538c385c7d678d03dc6a133fe0656ed0d64` (Linux JDK 17). The runner verifies the entire 452-entry file/link identity.
- `caddy`: `/usr/bin/caddy` extracted from `caddy@sha256:0c994536bddb66445885237f1a5dcc1916bccea922661c76b4e9fc24061f9b52` (2.11.4), SHA-256 `e1f904038fc11ca897ac5a12fdacfb2a7add02a8720c426d562a37f6fdad2afe`.
- `seccomp.json`: the derived `seccomp-browser-sandbox.json` from the pinned context preparation, SHA-256 `4196af2ea4c1921e0c1ab2891da6cb829308cfc2e9fe5f5fdf6fc4bead8665b7`.

Extract only public runtime files from owned stopped containers, then remove those containers. Do not include application secrets, TLS material or a browser profile. Python, OpenSSL and Docker must be available on the host. Existing Inspector support files are read from `--source`, an exact core source copy; they are hashed before/after the run.

## Run separately for each client and protocol era

```sh
python3 interop/self-issued/run.py \
  --source /absolute/exact/core-source --runtime /absolute/private/runtime \
  --app /absolute/private/app --app-manifest /absolute/private/app-manifest.json \
  --output /absolute/new/private/public-legacy \
  --client-type public --era legacy --port 37281
```

Repeat with `confidential` and/or `modern`, a new output directory and a never-used issuer port (10000–60000). Ports identify fresh demonstration namespaces; never restore or restart an established issuer using fresh keys/volatile state. The default `--return-mode exact-native` callback is exactly `http://127.0.0.1:6274/oauth/callback`; the registered native IP loopback option is explicit. Use `--return-mode native-port` to register only `http://127.0.0.1:6273/oauth/callback` while the released client requests and redeems `http://127.0.0.1:6274/oauth/callback`. The explicit browser CORS origin is the actual port; consent policy uses the checked interaction return. Use `--return-mode https` for the client UI and exact callback at `https://localhost:6276/oauth/callback`, served by the private-CA TLS edge forwarding to the unmodified Inspector backend. Its origin allowlist is explicitly configured. Both TLS origins retain normal hostname/certificate validation; no forwarding scheme/identity is trusted by the issuer. All modes verify the exact requested redirect URI on the actual token exchange. Those web UI modes test a concrete different native port. The separate native executable modes below exercise client-owned OS port allocation.

The pinned framework requires the public MCP port to equal its listener port. The fixture preserves the public Host authority and binds the TLS edge to IPv6 loopback and the MCP app to IPv4 loopback at that same port. Browser/Node DNS selection is confined to the isolated fixture. The local HTTP observer forwards requests/responses and records structural method/status/authentication facts; it is verification infrastructure, not a replacement library HTTP layer or a production edge.

The run creates a disposable CA/leaf and trusts it only in private NSS/Node stores (and a child-local Java truststore in CIMD mode). Certificate/hostname validation and Chromium sandboxing stay enabled. Docker uses network isolation, non-root execution, dropped capabilities and the scoped seccomp profile. Runtime/application/module mounts are read-only. No global trust or host policy is changed.

## Recovery modes

`--recovery none` retains the normal flow. Use `--recovery expiry` to wait beyond the initial token's actual advertised lifetime (119–120 integer seconds for the example's two-minute setting), then execute a tool through the ordinary UI. The fixture requires a real expired-token401, exactly one automatic refresh using the current refresh value and same client/resource, changed access/refresh values, and a successful tool call using the new access value. No clock is changed and no credential or OAuth result is injected. This path requires no second browser authorization or manual reconnect.

Use `--recovery step-up` to begin with only `mcp:discover`. The actual `whoami` call must fail with403 `insufficient_scope`. The client's normal recovery requests a second authorization; fresh app consent displays both scopes and the checked return. A second S256 code exchange must grant the expanded scope, with zero refresh attempts used to widen it. The fixture allows a normal tool retry after the interactive callback and records whether it was needed; that retry is not automatic replay of the original operation. Application tenant/object denial stays denial.

Recovery runs retain the existing normal-flow CORS/control and application-denial checks. They are bounded to one refresh for expiry, one insufficient-scope denial/two code grants for step-up, and at most four expired bearer rejections. Structural phase receipts keep long real-time waits observable. Token equality/rotation comparisons occur only in volatile memory; neither values nor credential hashes enter evidence. Each recovery invocation has a five-minute run limit, including the real expiry wait. Run the modes separately with new output directories and never-used issuer ports.

## Second resource

Use `--second-resource` with `--recovery none` to enable the example's optional `/mcp-second` endpoint. The released client has two separately configured server URLs. After the first ordinary flow and its policy/CORS checks, the fixture uses normal disconnect/connect UI controls for the second server, approves fresh resource-specific consent, and requires another S256/exact-resource code exchange plus initialize/discover, list and tool call with that resource's own token. No access/refresh values or OAuth results are injected into the client.

Separately labeled diagnostic probes reuse the two genuine client-issued access values only in the observer's volatile memory. They make ten ordinary TLS requests: list/call with each token at its own endpoint, list/call with each token at the other endpoint, then successful own-resource calls after the rejections. Cross-resource requests must return401 `invalid_token` with the target's exact metadata challenge and no successful tool result. Both endpoints share issuer keys, clients and scope names, so this exercises actual resource binding. These probes test server rejection; they are not claims that the released client itself sent the other resource's token. Normal consumer traffic is separately labeled and must not reuse the first resource's token at the second endpoint.

The diagnostic probes use modern sessionless MCP framing regardless of the selected consumer era. They do not alter the client's requests or responses, patch its code, or suppress a challenge. Token values and hashes never enter receipts. The disposable process, keys and browser cleanup rules remain the same.

## Evidence and scope

`RUN.json`, `junit.xml` and `evidence/RESULT.json` contain actual structural assertions, source/artifact/runtime identities, bounded method/status facts and cleanup results. Failed runs remain failures. No raw logs, request/response bodies, credentials, credential hashes, cookies, browser profiles or TLS private keys are retained. Owned child processes/containers and private state are removed after success or failure.

Checks cover checked client/resource/callback/S256 binding, exact token return binding, native port variation or HTTPS return when selected; public or Basic confidential exchange without ambient cookies; secure host cookie and login session/CSRF rotation; credential callback without Referer; initialized/discovered MCP, tool catalog, permitted call and tenant denial; real browser metadata/token CORS, actual token OPTIONS, disallowed direct MCP browser access, and rejected unregistered browser origins (a separate static page at `http://127.0.0.1:6275`).

The normal mode qualifies only its preregistered flow. A passing selected recovery mode supplies scoped real-expiry/automatic-refresh or interactive scope-step-up evidence on the same volatile single-process example. The optional second-resource mode supplies normal independent consumer authorization and separately identified cross-resource server rejection evidence. It does not resolve the known released-client generic403-without-challenge limitation or qualify signing-key rotation, durable browser deployment, HA or distributed admission. Native executable scope is described below. RC-1/RC-AS and broader release obligations remain open. The example still requires an appropriate trusted production framing/duplicate-header boundary; this ordinary-flow Caddy fixture supplies no new comprehensive framing qualification.

## Client metadata documents

Use `--client-type cimd --return-mode https`, separately for `legacy` and `modern`; `--recovery expiry` also exercises automatic refresh. CIMD mode uses the released client's normal `client.json` configuration (`cimd.enabled` and `cimd.clientMetadataUrl`), with no preregistered client ID, injected OAuth result or DCR fallback. The actual issuer advertises CIMD and fetches `https://cimd.example.com:6277/client.json` through the existing Revetsec pinned HTTPS transport. The private document allows the exact HTTPS return, S256 code and rotating refresh; ordinary browser login/consent and resource permission checks still run.

The runner requires an already cached immutable Alpine namespace image `sha256:28bd5fe8b56d1bd048e5babf5b10710ebe0bae67db86916198a6eec434943f8b` (arm64). A disposable network-none namespace owner receives `8.8.8.8/32` and a local `fd00::1/128` alias on `lo`, with only NET_ADMIN for this configuration. It shares no host/external network or published ports. This is a public-form numeric peer isolated inside the fixture, not an external service or claim of hostname ownership. The browser/application container shares only this owned namespace, remains uid1001 with zero effective capabilities, and verifies loopback-only addressed interfaces/no external routes. The IPv6 alias preserves Node ADDRCONFIG IPv6-first localhost selection for the TLS edge; only the configured public-form IPv4 peer is returned to the metadata resolver. Both containers are removed after success or failure. No image is pulled.

The private leaf includes the metadata hostname. The Java child imports only this invocation's CA into a private truststore and receives child-local JVM trust properties; default PKIX and hostname checks remain active. Caddy listens on the isolated numeric peer, preserves the original Host, and reports the actual TLS SNI structurally to the observer. No certificate error bypass, global trust mutation, implicit public DNS or private-address policy exception is used.

The observer serves a bounded cacheable document with `max-age=300`, and retains only method/status/Host/SNI/byte-count/header-presence facts. ## Native executable and ephemeral IP callbacks

Use `--return-mode native-ephemeral-ipv4` or `native-ephemeral-ipv6` with a preregistered public/confidential client, `--recovery none`, and no second resource. The unmodified released Inspector CLI starts its own callback listener through its ordinary `--callback-url http://127.0.0.1:0/oauth/callback` or `http://[::1]:0/oauth/callback` configuration. The OS selects the port; the fixture neither reserves it nor supplies a callback server. Native modes add an exact `::1` resolver exclusion for Chromium, alongside the existing127.0.0.1 exclusion; all other hostnames remain blocked except the explicitly mapped issuer localhost. The offline namespace and request allowlist stay enforced. Registration stays at port6273 with the explicit native exception. Only the selected port may differ. Owned process descriptors identify the actual listening IP family/port; structural receipts require it to equal the authorization return, and the token request must exactly bind that same selected URI.

Sandboxed Chromium opens the CLI's ordinary printed authorization URL, then submits normal application login/consent. For IPv6, the example renders an escaped checked **Return to application** link after consent, which the user clicks normally. This preserves same-origin form CSP without an unsupported IPv6 host source or broad HTTP exception. Both families send the actual browser callback to the native listener. The CLI uses its supported private file secret store, deleted at shutdown. Separate CLI processes run `tools/call` with `--stored-auth-only`, using only their own naturally persisted grant for a permitted operation and tenant denial. No `--use-stored-auth`, bearer injection, OAuth state injection or client patch is used. `--native-followup-era modern` selects ordinary modern negotiation for these saved-grant calls after an initial legacy authorization; omitted, it uses the initial `--era`. Receipts distinguish those two eras. They do not claim fresh modern authorization from a stored-grant followup. The application browser origin is the issuer for these native modes; browser CORS evidence comes from the separate web UI modes.

Fresh `--era modern` with the pinned Inspector2.9.0 CLI and port0 currently fails: its modern recovery path captures the authorization URL before listener allocation and retains redirect port0 after opening the real nonzero listener. Revetsec rejects that request with400. The failed attempt is retained; the client is not patched and the issuer does not accept port0. This limit is separate from successful legacy native authorization plus modern saved-grant calls. The runner allows fresh modern attempts and preserves failures with bounded structural facts only. Native callback port0 behavior, initial negotiation and saved-grant behavior must be interpreted separately. These local native modes retain the volatile issuer, private TLS, browser sandbox, offline images, immutable client tree and full cleanup boundaries of the other modes.
